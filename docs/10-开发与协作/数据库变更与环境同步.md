# 数据库变更与环境同步

## 原则

- 数据库结构通过版本化迁移同步，不复制本地数据库。
- 系统基础数据通过幂等 Seed 同步；本地和自动化测试业务数据不得进入共享环境。
- 迁移链由数据库/集成负责人串行管理；已合并或已部署迁移不得改写。
- 代码回滚与数据库恢复分别评估，不能假定 `git revert` 会撤销 schema。

## 分支阶段

1. 在 Issue 的数据库变更区声明表、字段、索引、数据回填、兼容性和风险。
2. 从最新 `main` 领取下一 revision。
3. 在独立 `tradeez_dev_<task>` 数据库开发。
4. 验证空库建立和受支持旧版本升级两条路径。
5. 在 PR 中提交迁移、代码、测试、恢复策略和不可逆说明。

当前迁移事实源为 `backend/app/migrations.py` 的 `SCHEMA_VERSION`、`_MIGRATION_STEPS` 和 `backend/migrations/`。应用启动可能自动升级目标库，启动前必须确认数据库名称和环境。

## PR 验证

CI 为每个 PR 创建隔离 PostgreSQL 服务，执行全部迁移、Seed 和后端测试。PR 不得连接共享生产测试库。迁移冲突必须在合并前从最新 `main` 重排并重新验证。

## main 到生产测试环境

```text
main CI 通过
→ 构建不可变版本
→ GitHub Environment 审批
→ 备份并记录恢复点
→ 执行尚未应用的迁移
→ 执行幂等系统 Seed
→ 核对 schema version
→ 部署对应代码
→ API/浏览器健康检查
→ 在部署记录和 PR 回填结果
```

连接串只保存在 GitHub Environment Secrets。新增表、可空字段等兼容变更可按审批策略自动执行；删除表/字段、类型改变、大量回填、唯一约束和权限改变必须人工审批并准备维护窗口。

## 失败和恢复

迁移失败立即停止代码部署，保留日志并判断是否部分执行。优先增加修复/补偿迁移，不手工伪造版本；任何紧急手工操作都必须形成 Issue、可复现脚本和审计记录。高风险迁移先采用扩展/迁移数据/切换代码/清理旧结构的多阶段方式。
