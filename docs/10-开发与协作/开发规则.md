# 开发规则

## 交付单元

一个可验收任务对应一个 GitHub Issue、一个分支、一个 worktree、一个主要编码者和一个 PR。大模块使用 Epic 和有依赖关系的子 Issue 拆分，不在一个分支长期堆积多个阶段。

## 阶段门禁

| 阶段 | 允许工作 | 必需证据 | 进入下一阶段条件 |
|---|---|---|---|
| Research | 观察和记录参考产品 | URL、路径、截图、状态、数据关系 | 研究负责人复核 |
| Requirement Review | 功能矩阵和边界 | P0/P1/P2、异常、权限、响应式 | 产品负责人确认 |
| Frontend Mock | 页面、交互、Mock 数据逻辑 | 浏览器证据、共享类型、状态矩阵 | 产品负责人确认 |
| Backend | API、权限、服务和迁移 | API/迁移契约、测试 | 技术审查通过 |
| Integration | 切换真实接口 | 加载、空、错误、并发和一致性证据 | 联调通过 |
| Testing | 全量适用门禁 | CI、Playwright、风险和回滚 | 可进入 PR Review |
| PR Review | 审查和修正 | 审查记录、确认记录 | 必需审查与检查通过 |

不得跳过产品确认直接由 Mock 进入后端。研究或 Mock 阶段 PR 使用 `Refs #Issue`，只有整个 Issue 验收完成时使用 `Closes #Issue`。

## 职责

- 产品负责人确认范围、优先级、Mock 和验收标准。
- 模块负责人维护 Issue、规格、实现和证据。
- 技术/集成负责人管理共享资源、Review、CI 和合并。
- 数据库负责人分配迁移 revision，审核环境同步。
- AI 只执行当前 Issue 已授权的阶段和范围；不把推测写成事实。

## 串行资源

数据库迁移链、依赖锁文件、全局导航、全局 Token、共享契约、CODEOWNERS 和发布配置必须在 Issue 登记。优先创建独立共享 PR 并合并，再让业务分支 rebase。

## 完成定义

- 范围、确认和验收证据可追溯。
- 代码、类型、接口、schema 和文档一致。
- 适用质量门禁通过，没有隐瞒的跳过项。
- 风险、兼容性、数据库影响和回滚明确。
- GitHub Project、Issue 和 PR 状态已更新。
- 长期事实进入唯一模块规格；临时过程留在 GitHub。
