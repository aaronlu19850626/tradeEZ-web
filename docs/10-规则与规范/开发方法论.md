# TradeEZ Web 开发方法论

## 目标

在现有雏形上进行可追踪、可回退、分阶段验收的迭代。需求未确认前不进入业务开发；每个阶段完成验收后才进入下一阶段。

## 开发约束

1. 先确认需求，再设计数据结构、功能清单和界面方案，最后实现。
2. 每次只处理一个明确的模块或变更包，禁止顺手扩大范围。
3. 涉及数据结构的变更必须同步更新 API、迁移脚本、测试数据和文档。
4. 删除或重命名功能前，先记录影响范围、替代方案和回滚方式。
5. 前后端接口以契约为准；接口变更必须说明兼容策略。
6. 不以“能打开页面”作为完成标准，必须有可复现的验收用例。
7. 每次开发结束都更新 `项目进度.md`，记录完成项、未决项、风险和下一步。
8. 未经确认不修改生产部署、账号、密钥和历史数据。
9. 业务模块统一采用“先前端、后后端”的开发门禁：先使用明确标注的 mock 数据完成页面、状态和交互；前端方案经用户确认后，才开发数据库迁移和后端接口。
10. 后端接口开发完成后，必须将前端从 mock 切换到真实接口，并执行接口、页面交互、异常路径和数据一致性测试；当前任务完成测试前不得越过自身阶段门禁，互不依赖的其他模块可以在独立 Issue、分支和 worktree 中并行。
11. mock 数据不得伪装成生产数据或写入远程数据库；mock 与真实接口必须共享已确认的类型/API 契约，便于切换和回归。
12. 已有业务模块不做局部改造或持续打补丁；新需求必须在新模块目录、组件和服务中完整重写。原模块源码、路由、接口和服务作为“待下线旧模块”隔离保留，不再新增功能或被新模块依赖。
13. 新模块完成前端 mock 确认、后端联调和阶段验收后，才按清单逐项删除对应旧页面、旧组件、旧接口、旧服务和无用迁移/类型，并完成删除后的回归测试；删除前必须记录影响范围、替代关系和回滚点。
14. 系统同时支持中文和英文；文案、日期、数字和状态标签必须通过全局国际化资源和语言切换处理，新模块不得继续散落硬编码单语文案。已有模块按重写计划逐步接入全局国际化，不在旧模块上做局部补丁。
15. 全局数据展示遵循高级分析工作台基线：表头使用稳定的中性层次色，正文/辅助信息/状态通过字号、字重、颜色和标签分层；金额、时间、数量和状态保持清晰的视觉优先级。
16. 数据表格的主要操作默认直接放在行内操作区，不使用承载核心功能的悬浮菜单或右侧抽屉；危险操作仍通过居中确认模态框完成。该视觉与交互基线适用于后续所有模块，不再逐模块重复说明。
17. 全局视觉规则以《全局样式规则.md》为唯一执行基线；新模块直接复用现有 Token、组件和交互语义，不另起一套颜色、尺寸或 Tooltip 规则。
18. 项目文档统一使用中文文件名；新增文档必须先登记到《项目文档索引.md》，并在开头写明用途、状态、依赖和验收入口，保证迁移到新环境后可以按索引快速恢复上下文。
19. 存在可访问的参考产品时，前端开发必须按功能点逐个通过专用研究浏览器/CDP 实际观察，禁止凭记忆或想象实现。每个功能点开始前都要检查对应页面、列表、详情、弹窗和控件的布局、层级、间距、图标、字体、颜色、状态、弹层位置、hover/focus/loading/error 和交互反馈；观察后映射到 TradeEZ 的 Token、标准控件和产品规则。参考产品中无法观察到对应实现时，不暂停开发，但必须依据 TradeEZ UI 规范自主设计，并登记到《前端自主设计清单》，作为用户评审范围。不得直接复制参考产品的品牌、文案、配色或专属视觉。
20. 参考产品的视觉复刻必须执行“截图 + DOM/CSS 数值 + 用户圈差异”闭环（见《前端开发强制规则》第 12 节）：先截图并抓取真实 DOM/CSS 形成对照表，再逐功能点实现和截图对比，最后由用户看截图或页面圈出差异逐处修正；禁止只凭 DOM 数值判断视觉，禁止模块写完后一次性回找差距。

## 标准流程

### 阶段 0：现状盘点

记录当前页面、路由、接口、表结构、已知问题和雏形中可复用部分。

存在参考产品时，必须进入专用研究浏览器实际观察目标模块，并记录：

- 页面信息架构和导航
- 列表、详情、弹窗和表单流程
- 图标、字体层级、间距和状态表现
- 新增、编辑、删除、筛选和异常反馈
- 可借鉴的交互模式
- 不应照搬的品牌和视觉元素

阶段 0 的模块级盘点不能替代功能点级观察。进入某个具体功能点实现前，必须再次打开参考产品的对应状态，记录至少：

- 参考 URL、页面路径和操作路径
- 默认、hover、focus、active、disabled、loading、empty、error 状态
- 控件尺寸、间距、对齐、图标、字体和层级
- 弹层位置、打开和关闭方式、键盘行为和滚动行为
- 参考行为到 TradeEZ 标准组件的映射
- 无法观察或需要 TradeEZ 自主设计的部分，并登记到《前端自主设计清单》

### 阶段 1：需求确认

输出：用户故事、范围边界、功能清单、非功能要求、优先级和验收标准。此阶段不写业务代码。

### 阶段 2：方案确认

输出：数据模型/API 契约、状态流转、权限规则、页面信息架构和界面草案。确认后冻结本阶段范围。

### 阶段 3A：前端原型（Mock）

使用 mock 数据实现页面结构、加载/空状态、成功/失败状态、交互流程和响应式表现。此阶段不新增后端接口、不修改远程数据库；完成后提交用户进行前端交互确认。
新模块使用独立目录和独立组件实现，不修改原模块页面和组件；旧模块仅作为行为和数据兼容参考。
编码前必须确认已经完成参考产品研究，并把观察结论映射到 TradeEZ 的 UI 规范。参考产品观察结果不能替代现有全局组件和视觉门禁。

### 阶段 3B：后端实现

前端 mock 方案确认后，再按已冻结的契约实现数据库迁移、服务层、API、权限和审计逻辑，并保留兼容处理。

### 阶段 3C：真实数据接入

后端接口通过自测后，将前端从 mock 切换到真实接口；每个小变更保持可运行。

### 阶段 3D：旧模块下线

新模块验收通过后，建立旧模块下线清单，逐项移除旧路由、页面、组件、接口、服务和无用类型；确认无引用后再删除，删除后执行完整回归检查。

### 阶段 4：测试与阶段验收

先执行后端接口测试，再执行前端真实接口联调和功能验收，覆盖异常路径、权限边界、数据一致性、响应式显示和回归检查。验收通过后才开始下一阶段。

### 阶段 5：沉淀

更新进度台账、变更记录、接口文档和操作说明；必要时建立回滚点。

## 验收规则

验收结果只能是：通过、部分通过（列出遗留项）、不通过（列出阻塞原因）。任何未决项都进入进度台账，不口头带过。
