# TradeEZ Web 前端开发强制规则

版本：1.0；状态：已确认，强制遵守。

本文是前端开发的第一道门禁。任何新增、修改、重构、修复或视觉调整，都必须先完成本文规定的规则检查，再进入编码。

## 1. 不可违反的三条总原则

### 1.1 标准语义控件优先

所有设计元素必须优先使用现有的标准语义控件。非标准语义控件默认禁止使用，必须先提交用户评审，评审通过后才能实现。

标准语义控件包括但不限于：

- 操作：`Button`、`ToggleGroup`
- 选择：`Checkbox`、`RadioGroup`、`Select`
- 输入：`Input`、`Textarea`、`InputGroup`
- 导航：`Tabs`、`Pagination`、侧栏导航
- 覆盖层：`Dialog`、`DropdownMenu`、`Popover`、`Tooltip`
- 数据展示：`Badge`、`Table`、共享 `DataTable`、共享 `SymbolBadge`、共享 `InfoTip`
- 日期：`Calendar`、共享 `DatePickerField`、日期范围 `Calendar mode="range"`

判断标准不是“长得像”，而是必须同时满足：

1. 使用正确的 HTML / ARIA 语义。
2. 使用全局组件及全局变体。
3. 支持键盘、焦点、禁用、加载和错误状态。
4. 支持 Light / Dark 主题。
5. 支持中文 / 英文。
6. 支持移动端、桌面端和局部溢出。

### 1.2 与现有三模块设计保持一致

新页面和新组件必须延续以下现有模块的整体设计理念：

- 交易总览：信息密度高、面板统一、图表克制、筛选与加载反馈明确。
- 交易账户：表单和账户数据清晰、风险操作分级、平台与币种选择统一。
- 交易记录：筛选查询完整、分组明确、DataTable 统一、日期筛选和日历语义一致。

不能只为当前页面创造一套新的按钮、徽标、输入框、表格、弹窗、Tooltip、筛选器或状态色。

### 1.3 编码前先执行本规则

任何开发开始前，必须先完成“开发前检查”和“控件映射”。如果存在标准控件无法覆盖的元素，必须暂停编码并提交评审。

## 2. 标准控件优先级

按照以下顺序选择实现方式，不能跨级：

1. 使用 `frontend/src/components/ui/` 中的现有组件。
2. 使用现有共享业务组件，例如 `DataTable`、`InfoTip`、`SymbolBadge`、`DatePickerField`、`DialogBody`。
3. 如果只是业务语义包装，放到 `frontend/src/components/` 或模块 `_components/`，底层仍使用标准组件。
4. 原生 HTML 控件只允许在标准组件无法表达且规范明确允许时使用。
5. 自定义控件必须先评审，评审通过后才能开发。

禁止直接修改：

- `frontend/src/components/ui/`
- `frontend/src/components/calendar/`

确需修改全局组件时，必须先说明影响范围、迁移方案和回归范围，并由用户确认。

## 3. 标准控件语义映射

| 需求 | 必须使用 | 禁止/慎用 |
|---|---|---|
| 执行动作 | `Button` | 可点击 `span`、`div`、Badge |
| 页面跳转 | `Link` | Button 伪装链接 |
| 多选 | `Checkbox` + Label | 自定义方块、Badge 勾选 |
| 单选 | `RadioGroup` | Button 模拟单选，除非是 ToggleGroup |
| 视图模式切换 | `ToggleGroup` 或 `Tabs` | 一组无状态 Button |
| 当前页/分页 | 全局 `Pagination` 语义 + Button | 纯文本模拟分页 |
| 菜单操作 | `DropdownMenu` | 自绘弹出层、悬浮 div |
| 轻量浮层 | `Popover` | 手写定位层 |
| 信息提示 | 共享 `InfoTip` | 自定义问号按钮、Badge |
| 模态流程 | `Dialog` + `DialogBody` | 抽屉承载核心编辑流程 |
| 状态标记 | `Badge` 语义变体 | 彩色 span、圆点 div |
| 业务数据表 | 共享 `DataTable` | 业务页手写 Table |
| 日期选择 | `Calendar` / `DatePickerField` | `input type=date` 跨浏览器控件 |
| 加载反馈 | 全局波形/Spinner/骨架 | 无反馈、阻塞式空白 |
| 空态/错误 | 标准空态与错误卡片 | 直接空白或 toast 代替页面状态 |

## 4. 非标准控件评审流程

如果标准控件确实无法满足需求，必须先提交评审，内容至少包含：

1. 控件名称和所属页面。
2. 使用场景和用户操作。
3. 为什么现有标准控件无法满足。
4. 交互状态：默认、hover、focus、active、disabled、loading、error。
5. 键盘和 ARIA 语义。
6. Light / Dark 表现。
7. 中文 / 英文长度适配。
8. 移动端和桌面端布局。
9. 是否可抽成共享组件。
10. 测试方案和风险。

在用户明确回复“评审通过”前，不得实现该非标准控件。

已确认的非标准例外必须记录在《项目进度》中，并说明允许范围和后续替换条件。

## 5. 三个模块的设计基线

### 5.1 交易总览

- 页面使用统一 Toolbar、筛选器、面板、图表和弹层组件。
- 面板固定模板、标题栏、底部栏、间距和加载遮罩必须沿用现有实现。
- 图表 Tooltip、坐标轴、Canvas/SVG 重绘和筛选刷新逻辑不得为单个面板另起标准。
- 总览的数据筛选、账户范围和日期范围必须与交易记录共用控件。

### 5.2 交易账户

- 页面头部按钮使用标准尺寸和变体。
- 账户表使用共享 DataTable 或标准 Table 语义。
- 新增账户的平台、币种、日期和表单控件必须复用现有选择组件。
- 行内仅保留高频操作，其他操作进入标准 DropdownMenu。
- 风险操作使用 warning/destructive，不使用自定义 amber/red。

### 5.3 交易记录

- 视图切换使用 ToggleGroup。
- 筛选触发使用 InputGroup + DropdownMenuTrigger + InputGroupButton。
- 日期范围和右侧月历使用 Calendar；盈亏只通过官方 DayButton 扩展。
- 交易表使用共享 DataTable，排序、分页、多选和批量操作遵循 shadcn Data Table 语义。
- 日视图、周视图和弹窗必须复用共享 TradeTable / TradeDayDetailDialog，不复制实现。
- 日视图默认 8 个日期分组、周视图默认 6 个周分组；仅第一组默认展开交易明细。

## 6. 开发前检查

开始编码前必须完成并输出以下检查：

### 6.1 规则读取

- 已阅读本文。
- 已阅读 UI 规范。
- 已阅读对应模块设计文档。
- 已检查共享组件和现有同类页面。

### 6.2 控件映射

逐项列出页面元素和对应标准组件：

| 页面元素 | 语义 | 标准组件 | 是否新增 | 是否需要评审 |
|---|---|---|---|---|
| 示例：批量操作 | 菜单操作 | DropdownMenu | 否 | 否 |

任何“未分类”“不确定”“准备自绘”的控件都必须先解决。

### 6.3 影响评估

- 是否涉及全局 Token、主题或基础组件。
- 是否涉及共享组件。
- 是否影响交易总览、交易账户、交易记录中的其他页面。
- 是否涉及接口、缓存、分页、加载或统计口径。
- 是否需要同步文档和测试。

### 6.4 开发前置门禁

满足以下条件才能开始编码：

- 所有元素都有标准控件映射。
- 不存在未经批准的非标准控件。
- 设计结构符合现有三模块。
- 加载、空、错误、禁用、溢出、双语和双主题路径已明确。
- 验收范围和测试方式已明确。

## 7. 编码规则

### 7.1 组件

- 不复制 Button、Badge、Input、Table、Dialog、Tooltip 的样式。
- 不通过 `className` 重写全局组件的核心尺寸、圆角、hover 或颜色，除非确有必要并经过评审。
- 不把一个交互控件嵌套在另一个交互控件内。
- 不用 Badge 承载可点击动作。
- 不用 Button 承载纯状态。

### 7.2 状态色

- 盈利/成功：`success` / `success-soft`
- 亏损/失败：`danger` / `danger-soft`
- 警告：`warning` / `warning-soft`
- 信息：`info` / `info-soft`
- 选中：`primary-soft`
- 中性：`secondary` / `muted` / `outline`

业务页面不得散落 hex、RGB、amber、red、green 等硬编码颜色。

### 7.3 数据展示

- 金额、时间、数量、R 倍数使用 `tabular-nums`。
- 缺失值使用 `N/A` 或 `--`，不能以 0 代替。
- 盈利亏损同时使用正负号和颜色。
- 状态、方向、标签使用 Badge；用户输入和数据正文使用普通文本。

### 7.4 布局

- 页面根容器、间距和最大宽度沿用 Dashboard shell。
- 不制造页面级横向滚动。
- 表格、筛选和日历允许局部滚动。
- 相同信息层级必须使用相同面板高度、标题栏高度、底部栏高度和对齐方式。
- 不把 Card 嵌套 Card。

### 7.5 交互与可访问性

- 所有按钮、菜单、复选框、单选框、开关和日期格必须有明确语义。
- 图标按钮必须有 `aria-label`。
- 键盘可操作，焦点可见，Escape、Enter、Tab 行为符合标准组件。
- 对话框必须使用 Header / Body / Footer 结构和受控焦点。
- Tooltip 不能成为唯一信息来源。

### 7.6 国际化和主题

- 新文案必须进入中英文资源，不得硬编码单语。
- 数字、日期、币种和排序必须使用当前 locale。
- 新页面必须同时验证 Light 和 Dark。
- 不能依赖颜色作为唯一状态表达。

## 8. 实现后验证

每个前端任务完成前必须执行：

1. TypeScript 类型检查。
2. Biome 检查。
3. `git diff --check`。
4. 浏览器视觉和交互验证。
5. 390px、768px、1024px、1440px 响应式检查。
6. Light / Dark 检查。
7. 中文 / 英文检查。
8. 加载、空、错误、禁用和局部滚动检查。
9. 三模块设计一致性检查。
10. 更新《项目进度》和对应设计文档。

如果验证未执行，必须明确说明原因和剩余风险，不能默认视为通过。

## 9. 禁止模式

- 业务页复制一份全局按钮、徽标、表格或弹窗。
- `role="button"` 的 span/div。
- 可点击 Badge。
- 嵌套 Button。
- 自绘下拉菜单、Tooltip、Checkbox、Radio 或 Dialog。
- 使用任意 hex 或框架外颜色。
- 页面元素贴边、不一致高度、无加载/空/错误状态。
- 仅在某一模块实现的控件没有复用评估。
- 规格未评审就自行创造新交互。
- 修改全局 UI 组件后不更新规范和组件总览页。

## 10. 验收结果

每个任务的评审结果只能是：

- 通过。
- 部分通过，并列出剩余项。
- 不通过，并列出阻塞原因。

所有未决项必须写入《项目进度》，不能只留在对话中。
