## 二、同步模块重构（契约变更）

### 2.1 变更背景

旧版同步存在以下问题：

1. 密钥格式要求 prefix.secret，由客户端生成，不安全
2. 游标基于成交时间（deal_time），且用 +1 秒跳过边界，可能漏单
3. 时间使用 MT5 服务器时区，与服务器时区不一致
4. 上传成交时隐式推进游标，没有独立的确认提交
5. Inp_MaxBatchSize 参数未实际使用

### 2.2 认证方式变更

旧：

- 密钥格式：prefix.secret
- 客户端分割后提取 secret 做签名
- Bearer Token 放完整密钥

新：

- 密钥由服务器生成，格式不透明（如 sk_live_xxx、sk_test_xxx）
- 客户端直接使用完整密钥作为 Bearer Token
- HMAC 签名使用完整密钥：HMAC-SHA256(secret_key, body + timestamp)
- 签名放在 X-Signature 头

### 2.3 时间统一为 UTC

所有时间字段统一使用 Unix UTC 秒：

- open_time：开仓时间（UTC）
- deal_time：成交时间（UTC）
- snapshot_time：快照时间（UTC）
- last_sync_time：游标时间（UTC）
- X-Timestamp：请求签名时间（UTC）

服务器不再需要 server_gmt_off 字段做时区转换。

### 2.4 游标定义变更

| 项目 | 旧 | 新 |
|------|----|----|
| 游标基准 | 最新一笔成交的 deal_time | 最新一笔订单的开仓时间（open_time） |
| 时区 | MT5 服务器时区 | UTC |
| 边界处理 | cursor + 1 秒（可能漏同秒订单） | 包含边界，同秒订单幂等重传 |
| 推进方式 | 上传成交时隐式推进（last_deal_time） | 独立接口显式提交 |

### 2.5 新增接口：更新游标

| 项目 | 值 |
|------|-----|
| Method | POST |
| Path | /api/v1/sync/update_last_sync_time |
| 用途 | 所有成交批次上传成功后，显式提交新的游标位置 |
| 前置条件 | 必须等所有成交批次都上传成功才能调用 |

请求体：

`json
{
  "mt5_login": 12345678,
  "last_sync_time": 1758186000
}
`

- last_sync_time：最新一笔已上传订单的开仓时间（UTC 秒）

成功（200）：

`json
{ "code": 0, "message": "ok" }
`

### 2.6 游标查询接口不变，返回值语义变更

POST /api/v1/sync/last_sync_time 接口路径不变，但：

- 返回的 last_sync_time 现在表示「最近一笔已同步订单的开仓时间（UTC）」
- 返回 0 表示从未同步过（客户端回溯近 7 日）

### 2.7 成交上传接口契约变更

POST /api/v1/ingest/deals 请求体变更：

移除字段：

- last_deal_time（不再通过上传接口推进游标）
- server_gmt_off（统一 UTC，不需要偏移）

新增字段（每笔 deal）：

- open_time：开仓时间（UTC 秒）

保留字段：

- mt5_login
- deals[] 数组

批量上传：

- 使用 Inp_MaxBatchSize 参数（默认 100，范围 1~1000）
- 同一批内的所有成交必须全部成功，失败则整批重试
- 全部批次成功后，调用 update_last_sync_time 提交游标

### 2.8 幂等保证

- 同一张订单（相同 ticket）重复上传，服务器应幂等处理（upsert by ticket）
- 边界同秒的订单会被客户端重复发送，服务器需按 ticket 去重
- 游标更新失败时，客户端下次同步会安全重传，不会丢单也不会重复

### 2.9 回退逻辑

- 若 last_sync_time 查询失败或返回 0 → 回溯近 7 天（UTC 时间）
- 若游标更新失败 → 已上传的成交已幂等落库，下次同步会重新上传但不会重复
