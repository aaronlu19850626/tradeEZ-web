# PostgreSQL 数据库迁移

版本：2.0；状态：已生效；用途：说明当前 PostgreSQL schema 初始化、迁移串行规则和验证方式；维护人：后端负责人/集成负责人；依赖：`backend/app/migrations.py`、`backend/migrations/`；验收入口：隔离数据库升级、后端测试与迁移 PR。

## 当前实现

- 运行数据库为 PostgreSQL，连接由 `TRADESYNC_DATABASE_URL` 提供。
- 当前代码中的 schema 版本以 `backend/app/migrations.py` 的 `SCHEMA_VERSION` 为唯一事实源；编写本文时为 `0039_account_market_profile`。
- 新空库由 `backend/migrations/postgres_schema.sql` 建立 `0022_postgresql_baseline`，再按 `_MIGRATION_STEPS` 顺序执行 `backend/migrations/versions/*.sql`。
- 已有数据库必须包含受支持的 `alembic_version`。有业务表却没有版本表时，启动会拒绝自动覆盖。
- 应用启动会调用 `upgrade_database()`。迁移开始前必须确认目标数据库，避免因启动开发服务而误升级其他环境。
- `backend/app/db.py` 保留少量 SQLite 风格 SQL 翻译兼容层；新代码应使用 PostgreSQL 语义，不能继续扩大兼容层。

## 新迁移规则

迁移链是串行资源。同一时间只允许一个分支修改：

- `backend/app/migrations.py`
- `backend/migrations/postgres_schema.sql`
- `backend/migrations/versions/`

集成负责人从最新 `main` 的 `SCHEMA_VERSION` 分配下一个 revision。每次迁移至少包含：

1. 新的 `.sql` 迁移文件；如仓库仍需要 Alembic 包装文件，则同时增加对应 `.py`。
2. `_MIGRATION_STEPS` 中从旧版本到新版本的单链映射。
3. 更新 `SCHEMA_VERSION`。
4. 新空库与旧版本升级两条验证路径。
5. 数据兼容、锁、失败回滚和不可逆操作说明。

已合并或部署的迁移不得改写。修正问题时增加后续 revision。

## 隔离验证

只在本任务的 `tradeez_dev_*`、`tradeez_test_*` 或临时迁移数据库验证，禁止直接对生产库试跑。启动前只显示数据库名称和环境，不在聊天、Issue 或日志中输出密码与完整 URL。

新空库验证：

```bash
cd backend
.venv/bin/python -c 'from app.migrations import upgrade_database; upgrade_database()'
```

随后核对：

```sql
SELECT version_num FROM alembic_version;
```

结果必须等于代码中的 `SCHEMA_VERSION`。对旧版本升级时先使用合成数据建立前一版本，再运行升级并验证数据、索引、约束和接口行为；不得通过删除版本表或手工篡改 revision 绕过检查。

后端门禁必须使用独立的 `tradeez_test_*` 数据库：

```bash
./scripts/quality/static.sh
```

有页面或数据流影响时再运行独立 `tradeez_e2e_*` 数据库的浏览器门禁。

## 旧 SQLite 迁移

旧 SQLite 数据导入 PostgreSQL 是独立运维操作，入口为 `backend/scripts/migrate_sqlite_to_pg.py`。执行前必须备份源文件、确认目标为空或满足脚本要求，并保留原同步密钥加密配置。该脚本不是日常 schema 升级方式，也不能用于测试数据库重建。

生产迁移、备份、恢复和密钥处理必须建立独立授权任务，并记录维护窗口、备份、验证、回滚点和实际环境负责人。
