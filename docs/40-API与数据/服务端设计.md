# TradeSync 服务端详细设计

版本：v0.2 历史设计；状态：仅作领域参考，需以当前代码和 Issue 复核；用途：追溯早期服务端闭环设计；维护人：后端负责人；验收入口：当前 API 契约、迁移链和测试。

版本 v0.2（基于 PRD / DESIGN / DATABASE v1.0 修订）  
目标：先交付 P0 最小闭环：注册登录 → 绑定 MT5 → EA 准实时同步 → 成交配对 → 每日盈亏与订单统计。

---

## 1. 需求拆解

### 1.1 P0 必须形成的闭环

1. 用户注册、登录、管理 MT5 账户。
2. 系统为每个 MT5 账户生成同步 Key。
3. EA 通过 HTTPS 上传：
   - 原始成交 `deals`
   - 账户快照 `snapshots`
   - 品种规格 `symbols`
   - 心跳 `heartbeat`
4. 服务端保证重复上传不重复入账，断网恢复后可补发。
5. 原始成交只追加、不提供普通修改接口。
6. 服务端将成交配对成完整持仓，而不是信任 EA 面板结果。
7. 服务端计算每日盈亏、订单列表、R 倍数、胜率、盈利因子、期望值等指标。
8. Web 端通过 REST API 查询账户、订单、盈亏曲线和统计图表。

### 1.2 P1 / P2 预留，但不阻塞 P0

- P1：纪律规则、违规检测、复盘笔记。
- P2：AI 盘前简报、行情数据、邮件 / Telegram 推送。
- P3：订阅支付、多账户对比、社区榜单。

### 1.3 最重要的产品不变量

1. **MT5 原始成交是唯一真相源。**
2. **策略必须按开仓成交识别，不能按平仓成交 magic 识别。**
3. **R 倍数必须用初始止损和品种规格计算；无止损则为 `NULL/N/A`。**
4. **统计日按北京时间 04:30 翻日。**
5. **所有时间统一存 UTC，统计日单独落库。**
6. **API 请求只做接收和查询，重统计逻辑放 Worker。**

## 2. 与原文档相比需要修正的点

| 问题 | 影响 | 本设计处理方式 |
|---|---|---|
| 文档同时写“Key 密文存储”和 `key_hash=sha256(secret)` | 哈希后无法还原，也无法主动生成 HMAC | 服务端不保存明文；请求到达后用请求里的 secret 验签，通过后只保存 `sha256(secret)` |
| 只有 timestamp，没有 request id | 5 分钟内仍可能重放 | 增加 `X-Request-Id` + Redis nonce，HMAC 签名覆盖 method/path/timestamp/request-id/body-hash |
| `server_max_ticket` 直接作为游标 | 乱序或历史补发时可能误清队列 | 响应逐条返回 accepted/duplicated/rejected；EA 只清除明确成功的 ticket |
| `symbols.tick_value` 注释与公式不一致 | 黄金等品种的 R 金额可能算错 | 增加 `tick_size`，公式为 `价格差 / tick_size * tick_value * volume` |
| `deals.position_id/symbol` 不允许空 | 出入金、余额修正等 MT5 balance deal 无法存储 | 增加 `deal_kind`，余额类成交允许 `position_id=NULL`、`symbol=NULL` |
| `daily_stats` 主键只有日和策略 | 无法支持方向、品种交叉统计 | 改成完整维度表，并生成必要 rollup 行 |
| 只有 `daily_stats`，缺账户级每日资金表 | 无法严谨表达日初余额、入金、出金、浮动盈亏 | 增加 `account_daily_stats` |
| `symbols` 只有当前规格 | 品种规格变化会影响历史 R 重算 | 增加规格版本表；配对后把 `planned_risk` 固化到 positions |
| 当前 EA 注释是 `TradeEZ-SC/TR`，文档示例是 `GoldSOP-SC/TR` | 策略识别可能写死 | 增加策略映射表，magic 和 comment 前缀均可配置 |

## 3. 总体架构

```text
MT5 EA SyncModule
   │  HTTPS + SyncKey + HMAC
   ▼
Nginx / TLS / 限流
   ▼
FastAPI Web API
   ├── Auth API             注册、登录、刷新令牌
   ├── Account API          绑定账户、Key 管理、同步状态
   ├── Ingest API           成交、快照、品种、心跳
   ├── Dashboard API        每日盈亏、净值曲线
   ├── Position API         订单查询、订单详情
   └── Stats API            策略/方向/品种/R 分布/热力图
   │
   ├──────────────┬───────────────┐
   ▼              ▼               ▼
PostgreSQL     Redis          Object Storage（后续 K 线/导出）
+TimescaleDB   缓存/限流/nonce
   ▲
   │
Celery Worker + Beat
   ├── pairing              deals → positions
   ├── account_daily_agg    日初/日终余额、已实现/浮动盈亏
   ├── trade_stats_agg      订单维度物化统计
   ├── retention            Free 7 天清理 / Pro 降采样
   ├── rules                P1
   ├── review               P1
   ├── crawler / ai_brief   P2
   └── notify               邮件 / Telegram
```

### 3.1 在线链路

- EA 请求必须快速返回。
- API 只做：鉴权、验签、校验、幂等写入、写 outbox、返回结果。
- 不在请求里做复杂配对和全量统计。

### 3.2 异步链路

- 成交写入后，通过 `task_outbox` 触发配对任务。
- 配对完成后，把受影响的统计日加入 `dirty_stat_days`。
- 统计 Worker 只重算受影响日期，保证准实时和可重放。


- payload hash 完全一致：返回 `duplicated`。

- 只有受控的数据修复命令可以处理异常数据，且必须留痕。

### 5.8 快照时序

`account_snapshots` 使用 TimescaleDB：

```sql
CREATE TABLE account_snapshots (
  account_id BIGINT NOT NULL,
  ts TIMESTAMPTZ NOT NULL,
  balance DOUBLE PRECISION,
  equity DOUBLE PRECISION,
  margin DOUBLE PRECISION,
  free_margin DOUBLE PRECISION,
  open_positions INT,
  raw_payload JSONB,
  PRIMARY KEY (account_id, ts)
);
```

建议保留策略：

- Free：原始快照保留 7 天。
- Pro：原始分钟级保留 90–180 天，更早压缩/降采样为 5 分钟、1 小时、1 天。
- 日统计长期保留。

## 6. 同步鉴权与防重放

### 6.1 请求头

EA 请求使用：

```http
Authorization: Bearer tsv.<prefix>.<secret>
X-Timestamp: 1753082193
X-Request-Id: 7f449d82-1ec7-4d1a-a506-60d1c6a51c23
X-Schema-Version: 1
X-Signature: <hex hmac>
```

### 6.2 签名原文

签名必须覆盖“未重新序列化的原始 body 字节”：

```text
<HTTP_METHOD>\n
<REQUEST_PATH>\n
<X-TIMESTAMP>\n
<X-REQUEST-ID>\n
sha256(<raw_body>)
```

服务端校验顺序：

1. 按 prefix 查找未吊销 Key。
2. 校验时间戳，允许 ±300 秒偏差。
3. Redis `SET NX` 检查 request id，TTL 10 分钟。
4. 用请求中的 secret 计算 HMAC，并做常数时间比较。
5. `sha256(secret)` 与数据库 hash 比对。
6. 更新 `last_used_at`。
7. 校验请求中的 `mt5_login/broker_server` 必须属于该 Key 的账户。

### 6.3 限流

- 每个 key prefix：默认每秒 5 次、每分钟 120 次。
- 每个 IP：注册/登录接口严格限流。
- 大批量上传走批量接口，不允许逐笔高频请求。
- 返回标准 `Retry-After` 和 `429`。

## 8. 时间与统计日

### 8.1 成交时间转换

EA 上传原始 `DEAL_TIME` 时，同时上传 `server_gmt_off`。服务端按：

```text
deal_time_utc = deal_time_server_epoch - server_gmt_off_seconds
```

例如 GMT+3 服务器上的本地 epoch 比真实 UTC epoch 多 10800 秒。

这个转换必须在 EA 联调时用一笔已知成交核对，避免 MT5 服务器“自动时间偏移”配置造成二次修正。

### 8.2 北京时间 04:30 翻日

```sql
stat_day = (
  deal_time_utc AT TIME ZONE 'Asia/Shanghai'
  - make_interval(hours => 4, mins => 30)
)::date
```

示例：

- 北京时间 2026-07-21 04:00 → 归属 2026-07-20。
- 北京时间 2026-07-21 04:30 → 归属 2026-07-21。

规则：

- `deals.stat_day`：按成交时间。
- `positions.stat_day`：按完全平仓时间。
- 未平仓 positions：`stat_day = NULL`。

## 9. 成交配对引擎

### 9.1 触发方式

1. `/ingest/deals` 写入新成交。
2. 同一事务写 `task_outbox`：任务类型 `pair_account_positions`，payload 为 account_id 和 position_id。
3. Worker 按 account_id 合并短时间内的多次任务，例如 1–2 秒 debounce。
4. 一个账户内的配对串行执行，避免部分平仓乱序并发。
5. 配对完成后写 `dirty_stat_days`。

### 9.2 单个 position 算法

对同一个 `(account_id, position_id)` 的成交按 `deal_time_utc, ticket` 排序：

1. 找最早的 IN 成交：
   - 方向 = IN.type。
   - 初始 SL = IN.sl_price。
   - 初始 TP = IN.tp_price。
   - 策略按 IN.magic / IN.comment 识别。
2. 汇总 IN / INOUT：
   - `volume_in`
   - 加权开仓价
   - `scale_in_count`
3. 汇总 OUT / INOUT：
   - `volume_out`
   - 加权平仓价
   - `net_pnl = profit + swap + commission`
4. 若 `volume_out >= volume_in - epsilon`：
   - `status=closed`
   - close_time = 最后一笔 OUT/INOUT 时间
   - hold_seconds = close_time - open_time
   - stat_day 按 close_time 计算
5. 否则：
   - `status=open`
   - `volume_remaining = volume_in - volume_out`
   - close_price 保持 NULL
6. 计算策略和 R：
   - SL 为 0/NULL：planned_risk=NULL，r_multiple=NULL。
   - 有 SL：按第 5.4 的品种规格公式计算。

并发控制使用 PostgreSQL advisory lock：

```sql
SELECT pg_advisory_xact_lock(hashtextextended(account_id || ':' || position_id, 0));
```

### 9.3 策略识别

默认映射：

| 标识 | 策略 |
|---|---|
| magic = 920717 | scalp |
| magic = 920718 | trend |
| comment 包含 `TradeEZ-SC` | scalp |
| comment 包含 `TradeEZ-TR` | trend |
| comment 包含旧前缀 `GoldSOP-SC` | scalp |
| comment 包含旧前缀 `GoldSOP-TR` | trend |
| 均不匹配 | manual |

识别优先级：

1. 开仓成交 magic 精确命中。
2. 开仓成交 comment 前缀/包含命中。
3. manual。

禁止使用平仓成交 magic 作为主要分类依据。若开仓成交因历史补发暂时缺失，position 先标记为 `pending_strategy`，待 IN 到达后重算。

### 9.4 部分平仓

- 支持 1 个 IN + N 个 OUT。
- P0 遇到多个 IN 时也可配对，但标记 `scale_in_count > 1`。
- 多 IN 的 P0 口径：用总成交量、加权开仓价和最早 IN 的初始 SL 计算风险；后续如产品确认加仓口径，再版本化调整。

## 10. 统计引擎

### 10.1 统计输入

订单统计只从 `positions` 生成：

- 只统计 `status=closed`。
- 按 `stat_day` 归日。
- 按账户、策略、方向、品种聚合。
- 余额类成交不进入订单胜率统计。

### 10.2 指标定义

```text
wins   = net_pnl > 0
losses = net_pnl < 0
evens  = net_pnl = 0

win_rate = wins / trades
gross_profit = sum(positive net_pnl)
gross_loss = abs(sum(negative net_pnl))
profit_factor = gross_profit / gross_loss
```

R 指标只统计 `r_multiple IS NOT NULL` 的交易：

```text
avg_r = avg(r_multiple)
avg_win_r = avg(r_multiple where net_pnl > 0)
avg_loss_r = avg(r_multiple where net_pnl < 0)   -- 保留负数
expectancy_r = win_rate_r * avg_win_r
             + loss_rate_r * avg_loss_r
```

无止损交易：

- `r_multiple = NULL`。
- 前端显示 N/A。
- 独立计入 `no_sl_count`。
- P1 纪律引擎中计入未设止损违规。

### 10.3 重算策略

- `dirty_stat_days` 唯一记录 `(account_id, stat_day)`。
- Worker 删除该账户该日相关 rollup 行后重算。
- 迟到成交可能同时影响旧平仓日和当前配对状态，因此插入/更新成交时要加入旧值和新值对应的日期。
- 提供 CLI 全量修复：

```bash
python -m app.cli recompute-positions --account-id 123 --from 2026-01-01 --to 2026-07-21
python -m app.cli recompute-stats --account-id 123 --from 2026-01-01 --to 2026-07-21
```

## 13. 多租户隔离

P0 必须同时做两层：

所有账户查询都必须经过授权依赖：


后续可启用 PostgreSQL RLS：

- API 开启事务后设置 `app.current_user_id`。
- Worker 使用内部角色并按任务 account_id 限定。
- RLS 作为最后一道防线，不能替代代码审查和集成测试。

## 15. 可靠性与数据修复

### 15.1 Outbox

API 写成交和写任务在同一个数据库事务中：

```text
BEGIN;
INSERT INTO deals ...;
INSERT INTO task_outbox ...;
COMMIT;
```

Worker 执行成功后把任务标记 done。失败按指数退避重试，并保留错误详情。

### 15.2 幂等

- 成交：`(account_id, ticket)`。
- 快照：`(account_id, ts)`。
- 品种：upsert 当前表，同时写规格版本。
- 请求批次：`request_id` 唯一。
- 统计：按账户 + 统计日删除后重建。

### 15.3 回填

需要提供管理命令：

- 重新拉取/接收 EA 历史成交。
- 重算 positions。
- 重算 account daily。
- 重算 trade stats。
- 校验 deals 总和、positions 净值、snapshots 余额。

### 15.4 对账

每日生成对账结果：

- balance deal 累计余额。
- 最近快照 balance/equity。
- positions 已实现盈亏。
- 若差异超过阈值，标记数据质量异常。

### 15.5 心跳写入路径与保留策略（2026-09-20）

心跳只用于“存活 + 最近一次元数据”，因此不需要每次请求都追加历史。规模上真正的风险是 `heartbeat_history` 无上限追加（实测单账号约 90–120 次/小时，1 万账号约 2500 万行/天），而不是请求速率本身。

实现：

- **历史采样**：`heartbeat_history` 每个账号默认每 300 秒最多写一行（`TRADESYNC_HEARTBEAT_HISTORY_INTERVAL_SECONDS`）。
- **重复写抑制**：若 `heartbeats.last_seen_at` 在写入窗口（默认 60 秒）内且元数据（货币/券商服务器/EA 版本/时区偏移）没有变化，直接返回 200 且不写库（`TRADESYNC_HEARTBEAT_WRITE_INTERVAL_SECONDS`）。
- **保留清理**：新增 `idx_heartbeat_history_time`（迁移 0027）让按时间裁剪走索引；API 进程每天执行一次清理，保留默认 30 天（`TRADESYNC_HEARTBEAT_HISTORY_RETENTION_DAYS`、`TRADESYNC_HEARTBEAT_HISTORY_AUTO_PRUNE`），并用 `pg_try_advisory_lock` 保证多实例下只有一个实例执行。也可用维护脚本手工执行：`python scripts/prune_heartbeat_history.py --days 30`。
- **限流定位**：心跳限流改为纯异常保护（每账号 30 次/分钟，默认 60 秒窗口），约为实测正常频率的 15 倍，不再承担“防止表膨胀”的职责。

线上注意事项：当前的限流器是进程内内存字典（`app/common/rate_limit.py`），多实例部署时每个实例各自计数；接入负载均衡后应把限流迁移到网关或 Redis，并让保留清理继续走数据库侧（本方案已经是数据库侧）。

## 21. P0 验收标准

1. EA 对同一批成交重复上传 10 次，数据库只保留一份，响应均为成功。
2. EA 断网 30 分钟后恢复，本地队列补发完成，服务端成交无遗漏。
