# MT5 服务器时区与夏令时方案

版本：0.2；状态：待评审。

## 1. 目标

解决 MT5 券商服务器不使用北京时间、且服务器时区存在夏令时变化时，历史成交时间可能偏移的问题。

核心约束：

- 交易用户不需要理解或维护时区。
- 页面继续统一按北京时间分日、分周和展示。
- 时区识别、偏移规则、夏令时切换和重算全部由系统自动处理。
- 无法确定时区的券商不影响同步，由系统内部标记并持续自动学习。

## 2. 核心方案

采用“原始时间双存 + 系统自动时区解析 + 自动重算”：

1. EA 上报 MT5 原始服务器时间、当前服务器 UTC 偏移和券商服务器名称。
2. 后端同时保存原始服务器时间和归一化 UTC 时间。
3. 后端通过券商目录、服务器名称和偏移变化自动解析时区规则。
4. 未识别时先使用当前偏移，用户页面仍正常展示。
5. 系统后续识别出准确时区或夏令时规则后，自动重算已有原始时间，不需要用户重置。

用户端不出现“时区”“夏令时”“UTC 偏移”等配置项。

## 3. EA 上报协议

### 3.1 成交事件

交易事件同时发送原始服务器时间与当前 UTC 时间：

```json
{
  "open_time": 1789631000,
  "deal_time": 1789632000,
  "server_open_time": 1789638200,
  "server_deal_time": 1789639200,
  "server_gmt_offset": 7200
}
```

- `open_time`、`deal_time`：EA 根据当前偏移转换出的 UTC 时间，保持旧版本兼容。
- `server_open_time`、`server_deal_time`：MT5 原始服务器时间。
- `server_gmt_offset`：同步时实时计算出的服务器 UTC 偏移。

### 3.2 心跳

心跳增加：

```json
{
  "server_gmt_offset": 7200,
  "server_timezone_name": "Europe/Athens",
  "broker_server": "XMGlobal-MT5 10"
}
```

`server_timezone_name` 只有在连接器能够确定时上报。无法确定时可以留空。

## 4. 后端内部数据模型

### 4.1 原始成交时间字段

`deals` 增加：

| 字段 | 说明 |
|---|---|
| `server_open_time` | MT5 原始开仓服务器时间 |
| `server_deal_time` | MT5 原始成交服务器时间 |
| `server_gmt_offset` | 收到事件时连接器上报的当前偏移 |
| `timezone_profile_id` | 系统最终匹配到的时区规则 |
| `time_normalized_at` | 最近一次 UTC 重算时间 |

现有 `open_time`、`deal_time` 继续作为页面使用的 UTC 时间。

### 4.2 券商时区目录

新增 `broker_timezone_profiles`：

| 字段 | 说明 |
|---|---|
| `id` | 规则 ID |
| `match_type` | `broker_server`、`broker_company`、`connector_hint`、`pattern` |
| `match_value` | 券商服务器或匹配规则 |
| `timezone_name` | IANA 时区，例如 `Europe/Athens` |
| `fixed_offset_seconds` | 固定偏移备用值 |
| `dst_profile` | `none`、`eu`、`us`、`uk`、`au` 或平台专用规则 |
| `confidence` | 规则置信度 |
| `enabled` | 是否启用 |

该目录由平台内部维护，不向交易用户展示。

### 4.3 未识别券商候选

新增 `broker_timezone_candidates`，记录系统自动观察到的：

- 券商名称
- 服务器名称
- 当前 UTC 偏移
- 首次和最近观察时间
- 是否发生过偏移切换
- 推测的夏令时规则
- 置信度和自动匹配结果

候选记录只用于系统内部学习和运营排查，不要求用户处理。

## 5. 自动识别优先级

系统按以下顺序自动选择时区规则：

1. `broker_server` 精确匹配。
2. `broker_company` 精确匹配。
3. 平台维护的服务器名称模式匹配。
4. 连接器明确上报的 IANA 时区。
5. 多次偏移样本推断出的固定偏移或夏令时规则。
6. 无匹配时使用最近一次上报的固定偏移。

无论命中哪一级，用户端流程都不变化。

## 6. 自动学习逻辑

每次心跳和同步都会记录：

```text
券商 + 服务器 + 观察时间 + 服务器时间 + UTC 时间 + 当前偏移
```

当同一券商持续出现偏移变化时，系统尝试匹配标准规则：

- 欧洲夏令时
- 英国夏令时
- 美国夏令时
- 澳洲夏令时
- 固定偏移

达到置信阈值后：

1. 自动建立或更新券商时区规则。
2. 将该券商已有账户关联到新规则。
3. 异步重算已有原始服务器时间。
4. 重新生成统一交易视图和统计数据。

整个过程不需要用户确认。

## 7. UTC 归一化逻辑

### 7.1 已匹配 IANA 时区

```text
原始服务器时间 + IANA 时区规则 -> UTC
```

能够正确覆盖历史夏令时变化。

### 7.2 只有固定偏移

```text
UTC = 原始服务器时间 - 固定偏移
```

适用于始终使用固定服务器时间的券商。

### 7.3 只有旧版 UTC 时间

继续使用 EA 已转换的 UTC 时间，不进行二次换算，保证旧数据兼容。

## 8. 自动重算

当时区规则新增、修正或置信度提升时：

1. 锁定受影响的原始成交范围。
2. 根据新的时区规则重新计算 UTC。
3. 更新 `deals.open_time`、`deals.deal_time`。
4. 重建受影响的 `trade_lifecycles`。
5. 使总览和交易记录缓存失效。
6. 记录重算版本和审计日志。

自动重算不依赖“重置交易”，不会清空用户数据，也不会要求用户重新同步。

## 9. 前端行为

用户端：

- 不显示时区设置。
- 不显示夏令时说明。
- 不要求用户选择 UTC 偏移。
- 不需要因为时区识别重新同步。

仅在系统内部管理端展示：

- 未识别券商
- 候选偏移规则
- 匹配置信度
- 自动重算状态和失败原因

## 10. 旧账户与新账户

旧账户：

- 下一次心跳和同步补充原始时间。
- 只有旧 UTC 时间时继续兼容。
- 系统识别规则后自动重算，无法重算的旧数据保留现状。

新账户：

- 从第一次同步开始同时保存原始时间和 UTC。
- 系统自动解析时区，无需创建时填写。

## 11. 测试

必须覆盖：

- 欧洲、英国、美国、澳洲夏令时开始和结束边界。
- 固定偏移服务器。
- 券商规则精确匹配和模式匹配。
- 偏移样本自动推断。
- 规则修正后的自动重算。
- 北京时间日切、周切和月度日历归属。
- 旧 EA 和旧历史数据兼容。

## 12. 开发阶段

1. 增加原始服务器时间字段和券商时区目录。
2. 后端实现时区解析、置信度和回退逻辑。
3. EA 增加原始服务器时间与实时偏移上报。
4. 实现自动重算和审计。
5. 建立内部未识别券商观察页。
6. 对 MT5 历史数据进行夏令时专项验收。

## 13. 验收标准

- 用户端没有时区或夏令时配置入口。
- 新账户创建时不增加任何时区填写步骤。
- 已知券商的历史成交在夏令时切换日前后时间正确。
- 未知券商仍可正常同步，不阻塞用户使用。
- 系统识别出准确规则后能够自动重算，无需用户重置。
- 页面继续统一按北京时间展示和统计。
