# 文档完整性审计（2026-09-24）

版本：1.0；状态：已完成；用途：验证新模型能否仅依赖仓库文档恢复工作；维护人：项目负责人；依赖：当前接手快照、文档索引、实际 Git；验收入口：链接检查、冲突检索和人工接手路径复核。

## 审计目标

新模型不读取历史聊天，也应能回答并执行以下事项：

1. 找到实际仓库、主干和当前提交。
2. 区分已经完成的主干治理、已有代码和尚未确认的一期产品范围。
3. 知道 Notebook 旧方案已经失效。
4. 安全启动前后端并排查本地 API 地址。
5. 创建 Issue、分支、worktree、独立数据库和 PR。
6. 按研究、需求确认、前端 Mock、后端、联调、测试和验收顺序工作。
7. 找到当前唯一下一步，并避免自行选择模块开工。

## 仍需由实际任务产生的内容

以下不是文档缺失，而是尚未开展的产品工作：

- TradeZella 核心模块全面盘点 Issue 与研究证据。
- TradeEZ 现有能力差距矩阵。
- 用户确认的一期范围、优先级和开发波次。
- 第一个真实业务模块的新流程演练记录。

现有模块和专项文档形成于不同阶段，不能批量声明为当前有效需求。它们应在对应模块进入研究 Issue 后逐份核对、更新状态或归档；在此之前，新模型只按当前接手快照、项目进度、当前 Issue 和代码使用它们。

## 接手验收提示

新模型首次进入后，应先执行只读核查并报告 Git、服务、文档和下一步。若它在没有 Issue 和用户一期确认的情况下直接开始 Notebook 或其他业务编码，或引用历史文档宣称模块已获验收，则接手失败。
