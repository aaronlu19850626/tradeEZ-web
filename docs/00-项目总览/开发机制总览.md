# TradeEZ 开发机制总览

版本：1.0；状态：已生效；用途：统一单人并行、多人协同、参考产品研究、前后端门禁和交接流程；维护人：项目负责人；验收入口：模块 PR 与 `scripts/quality/static.sh`。

## 1. 事实源

- GitHub `main` 是唯一事实源，主干必须保持可构建、可测试。
- GitHub Issue 记录需求、范围、负责人、阶段、阻塞和验收结论；PR 记录代码、测试、截图和审查。
- `docs/00-项目总览/项目进度.md` 只记录项目级摘要，不替代 Issue。
- 一个模块对应一个分支、一个 worktree、一个 Codex 任务和一个 PR。

## 2. 模块生命周期

```text
Issue 登记
  -> TradeZella/需求研究
  -> 功能点与验收评审
  -> 前端 Mock
  -> 用户确认前端和数据逻辑
  -> 后端接口与迁移
  -> 真实联调
  -> 静态门禁与 Playwright
  -> PR 审查与合并
  -> 进度、交接和下线记录
```

任何阶段未完成，都不得在 Issue 或进度文档中标记为完成。

## 3. 参考产品与产品规则

- TradeZella 作为页面结构、核心交互、状态和业务流程的参考。
- TradeEZ 的品牌、颜色、字体、文案、标准控件和可访问性规范优先。
- TradeZella 观察不到的行为，按用户描述和 TradeEZ 规范实现，并登记到《前端自主设计清单》。
- 参考行为与用户明确要求冲突时，以用户要求为准，并在功能点矩阵记录差异。

## 4. 完成定义

模块只有同时具备以下证据才能进入验收：需求 Issue、功能点覆盖矩阵、研究截图和 DOM/CSS 记录、前端确认记录、API 契约、测试结果、响应式与主题检查、风险和未决项。

## 5. 变更分类

当前工作树或新任务中的改动必须标记为：`已验收`、`开发中`、`实验性`、`治理`、`待清理`。未分类的改动不能进入新的模块分支，也不能被视为主干基线。
