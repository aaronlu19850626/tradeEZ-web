## 7. 性能结果

### 7.1 后端服务路径

数据规模：126,803 笔已平仓交易。

| 接口 | 优化前 | 优化后 |
|---|---:|---:|
| `/overview` 冷路径 | 约 10.1s | 约 3.1s |
| `/overview` 热路径 | 约 8.9s（浏览器初测） | 约 2.0s |
| `/summary` | 约 2.4s | 约 0.17s（热缓存） |
| `/groups?view=day&limit=8` | 约 3.8s | 约 0.24s |
| `/groups?view=week&limit=8` | 约 3.0s | 约 0.12s |
| `/calendar` | 约 5.7s | 约 0.02s |
| `/trades?page=1&page_size=100` | 未单独记录 | 约 0.15s |

### 7.2 真实浏览器 API 请求

- 最终总览请求 `/trades/overview?...from_day=2014-01-01&to_day=2026-09-22...`：约 3.3s
- 交易记录日分组 `/trades/groups?view=day&limit=8...`：约 1.66s
- 月历 `/trades/calendar?month=2026-09...`：约 21–43ms
- 账户列表 `/accounts`：约 30–125ms

### 7.3 已实施性能修复

- 总览散点只保留确定性采样的约 2,000 个点，并保留盈亏极值。
- 总览和汇总使用轻量 `LightTrade` 聚合对象，避免为 12.6 万笔交易构造完整 Pydantic `TradeItem`。
- 汇总累计曲线只返回约 1,000 个采样点，而不是 125,001 个点。
- 月历改为 `closed_trades` 的单一 SQL 聚合，不再加载全量交易后在 Python 中扫描。
- 日/周分组先按轻量对象确定分组，再只为选中的 8 个分组读取完整交易明细。
- 账户页交易数改为 `closed_trades` 投影计数，避免每个账户扫描 `deals`。
- 总览和交易记录在日期范围确定前不发起重数据请求，消除首屏重复请求。

## 8. 本轮发现并修复的问题

| 问题 | 根因 | 修复 | 状态 |
|---|---|---|---|
| 总览多品种筛选不更新统计和最近交易 | 前端只提交第一个品种，后端只接收单品种 | `symbol` 支持逗号分隔多品种，SQL 使用 `symbol IN (...)` | 已修复 |
| 全部视图排序只影响当前页 | 表格本地排序只处理当前页 | 排序改为服务端参数，排序后回第 1 页 | 已修复 |
| 分页无法跳转到指定页 | 只有上一页/下一页 | 增加页码输入框，回车/失焦跳转 | 已修复 |
| 总览首屏重复请求重数据 | 日期范围未初始化前先请求一次，初始化后再请求 | 日期范围确定前只取账户边界和品种，不请求总览/分组 | 已修复 |
| 月历接口大数据慢 | 全量加载交易后在 Python 中扫描 | 改为 `closed_trades` SQL 按日聚合 | 已修复 |
| 账户列表慢 | 每个账户扫描 `deals` 统计交易数 | 改为 `closed_trades` 投影计数 | 已修复 |
| 总览/汇总构造大量 Pydantic 对象 | 12.6 万笔交易全部构造 `TradeItem` | 聚合路径改用 `LightTrade` | 已修复 |
| 空账户首屏闪空态 | 账户范围未解析完就先渲染空态 | 增加初始加载判定 | 已修复 |
