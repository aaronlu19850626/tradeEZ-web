# TradeEZ 交易模块测试记录

日期：2026-09-22

## 1. 测试目标

对交易总览、交易记录、交易账户三个模块的筛选准确性、数据一致性和性能做一轮自主回归；发现的问题直接修复，并把结果固化到本文件。

## 2. 测试环境

- 后端：FastAPI，本地 `127.0.0.1:8000`
- 前端：Next.js，本地 `127.0.0.1:3000`
- 数据库：PostgreSQL `tradeez_dev`
- 测试用户：`chentodd@qq.com`（user id=1）
- 测试数据：4 个模拟账户 `Sim-Gold-A/B/C/D`，合计 125,000 笔交易、250,000 条成交，覆盖 2014–2025 年

## 3. 测试方法

1. 后端自动化测试：`backend/.venv/bin/python -m pytest -q`
2. API 数据准确性：直接调用 `trade_center.service` 的核心接口，并与 `closed_trades` SQL 结果交叉核对
3. 前端静态检查：`tsc --noEmit`、`biome check`
4. 前端定向构建：`/dashboard/overview`、`/dashboard/trade-center`
5. 性能计时：对 `/overview`、`/summary`、`/trades`、`/groups` 的底层服务路径做冷/热请求计时

说明：当前仓库未引入 Playwright，未执行真实浏览器端到端自动化；页面功能通过 API 级逻辑和定向生产构建覆盖。

## 5. 性能结果

数据规模：125,000 笔交易。

| 接口 | 优化前 | 优化后 |
|---|---:|---:|
| `/overview`（底层服务路径） | 约 10,100 ms | 约 2,400 ms |
| `/summary`（底层服务路径） | 约 2,400 ms | 约 2,400 ms |
| `/trades?page=1&page_size=100` | 未单独记录 | 约 150 ms |
| `/groups?view=day&limit=20` | 未单独记录 | 约 320 ms |
| `/groups?view=week&limit=20` | 未单独记录 | 约 135 ms |
| `/calendar` | 未单独记录 | 约 236 ms |
| `/bounds` | 未单独记录 | 约 34 ms |

优化说明：

- `/overview` 之前会对三类散点分别构建并排序全部 125,000 个 Pydantic 点，改为先构建轻量坐标再确定性采样，耗时从约 10s 降到约 2.4s。
- `/summary` 之前返回 125,001 个累计序列点，改为仅返回约 1,000 个确定性采样点，显著降低序列化与前端渲染成本。

## 6. 已发现并修复的问题

| 问题 | 修复 | 提交 |
|---|---|---|
| 多品种筛选只发送第一个品种，导致总览统计与最近交易不更新 | 后端 `symbol` 支持逗号分隔多品种，列表/分组/汇总按 `symbol IN (...)` 过滤，前端提交完整品种列表 | `20545b5` |
| 全部视图排序仅作用于当前页，且分页栏缺少跳转页 | 排序改为服务端排序、排序后回到第 1 页；分页栏增加页码输入跳转 | `20545b5` |
| 空账户/账户范围解析期间闪空态 | 首屏加载判定收紧，等待数据返回 | `94c2dd4` |
| 大数据量下总览接口慢、summary 序列过大 | 散点与累计序列服务端采样，见第 5 节 | 本轮 |

## 7. 残余风险与建议

- 未接入 Playwright，建议后续补浏览器端到端用例，覆盖真实点击、滚动、Tip 和弹窗交互。
- `/summary` 在 12.5 万笔规模下约 2.4s，后续可进一步把统计与累计曲线改为纯 SQL 聚合，或增加用户级汇总缓存。
- 当前性能结果基于本地单机，需在生产环境做同规模复测。

## 8. 结论

本轮筛选准确性、数据一致性和关键性能回归通过；发现并修复了多品种筛选、分页排序、空态闪烁和大数据序列采样问题。核心接口在 12.5 万笔数据规模下可用。
