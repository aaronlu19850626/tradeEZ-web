# PERF-001 性能优化报告

版本：1.0；状态：主体完成，后续总览接口层缓存定位待排期。

## 1. 目标与范围

本轮解决交易记录与交易总览在 10 万笔以上交易规模下的重复查询、全量回传和浏览器端聚合问题，范围包括：

- `/api/v1/trades/summary`
- `/api/v1/trades/groups`
- `/api/v1/trades/overview`
- 对应查询缓存和同步后的失效机制

本轮不改变交易记录、交易总览、交易账户三个模块的页面结构和用户操作流程。

## 2. 实施内容

### 2.1 SQL 汇总

- `summary` 的统计、累计净损益和抽样序列改为数据库聚合。
- `groups` 先通过 SQL 获取有交易的分组键，再只读取当前分页需要的分组交易明细。
- `overview` 的统计、评分输入、每日净损益、累计/回撤、最近 8 笔、一致性和散点抽样改为数据库聚合。
- 所有 SQL 路径复用同一套账户、日期、方向、结果、币种、市场和品种筛选条件。

### 2.2 评分口径

- 评分引擎拆分为“从逐笔交易计算”和“从聚合指标计算”两个入口，页面旧路径与 SQL 新路径共用同一套评分规则。
- R 倍数统一要求止损价格有效且大于 0；`sl_price=0` 不再被当作有效止损。
- 金额、R 倍数、累计曲线和回撤保留原有四舍五入口径。

### 2.3 固定像素桶散点

- 时段入点、时段出点和持仓时长三张散点图改为固定 256 个像素桶。
- 每个桶保留最小净损益和最大净损益两个边界点；小数据集直接返回原始坐标，不改变用户看到的数据精度。
- 持仓时长图按对数时间轴分桶，与前端图表坐标保持一致。
- 总览的累计净损益和回撤改为前端从服务端返回的唯一日线数据派生，避免响应中重复传输三份日线。

### 2.4 缓存

- 汇总、分组和总览对象使用 30 秒短 TTL 用户级缓存。
- 交易同步、账户重置、账户删除、账户导入和账户配置更新后统一清除该用户的缓存。
- 缓存只减少重复筛选请求，不替代 SQL 聚合和数据库投影表。

## 4. 性能结果

以下为稳定后端进程下的接口实测值：

| 接口 | 优化前 | 最终冷路径 | 最终热路径 | 响应体积 |
|---|---:|---:|---:|---:|
| `/summary` | 约 1.709s | 约 0.518s | 约 0.018s | 34.5KB |
| `/groups` 摘要 | 约 260KB | 约 0.18s | 按展开懒加载 | 19.5KB |
| `/group-trades` 单组明细 | 未拆分 | 约 0.02s | 展开后按需请求 | 3.2KB |
| `/overview` | 约 3.3s | 约 1.49s | 接口层约 1.5s，缓存命中未体现为端到端收益 | 292KB |

结论：

- 总览冷路径从约 3.3 秒降到约 1.49 秒，且不再把 12.7 万笔轻量交易构造到 Python 内存。
- 汇总冷路径从约 1.7 秒降到约 0.52 秒，热路径稳定在约 18 毫秒。
- 总览响应从约 816KB 降到约 292KB，散点从约 5,900 点降到约 1,404 点。
- 交易记录首屏先返回 8 至 9 个分组摘要，只有第一组默认加载明细；其他分组在用户展开时再请求。
- 分组摘要响应从约 260KB 降到约 19.5KB，服务端耗时约 0.17 秒，首个单日明细约 3.2KB。

## 7. 残余风险

- `/overview` 冷路径仍需约 1.49 秒，响应约 292KB；对象缓存已在服务函数内验证命中，但当前接口层重复请求仍约 1.5 秒，后续需继续定位进程路由或响应层开销。
- 单组明细约 3.2KB 且需要支持表格列动态切换，继续按列裁剪字段的收益低，暂不实施。
- 当前缓存为单进程内存缓存，多实例部署时需要替换为 Redis 或带版本号的共享缓存。

## 8. 结论

`PERF-001` 的主体目标已经完成：汇总、分组键和总览统计不再依赖浏览器全量交易，总览使用固定像素桶，交易记录按分组懒加载，筛选变化不会重复执行 Python 全量聚合。后续只需继续定位总览接口层缓存未命中现象。
