# PERF-001 性能优化报告

版本：1.0；状态：主体完成，后续像素桶优化待排期。

## 1. 目标与范围

本轮解决交易记录与交易总览在 10 万笔以上交易规模下的重复查询、全量回传和浏览器端聚合问题，范围包括：

- `/api/v1/trades/summary`
- `/api/v1/trades/groups`
- `/api/v1/trades/overview`
- 对应查询缓存和同步后的失效机制

本轮不改变交易记录、交易总览、交易账户三个模块的页面结构和用户操作流程。

## 2. 实施内容

### 2.1 SQL 汇总

- `summary` 的统计、累计净损益和抽样序列改为数据库聚合。
- `groups` 先通过 SQL 获取有交易的分组键，再只读取当前分页需要的分组交易明细。
- `overview` 的统计、评分输入、每日净损益、累计/回撤、最近 8 笔、一致性和散点抽样改为数据库聚合。
- 所有 SQL 路径复用同一套账户、日期、方向、结果、币种、市场和品种筛选条件。

### 2.2 评分口径

- 评分引擎拆分为“从逐笔交易计算”和“从聚合指标计算”两个入口，页面旧路径与 SQL 新路径共用同一套评分规则。
- R 倍数统一要求止损价格有效且大于 0；`sl_price=0` 不再被当作有效止损。
- 金额、R 倍数、累计曲线和回撤保留原有四舍五入口径。

### 2.3 散点抽样

- 时段入点、时段出点和持仓时长三张散点图均由数据库先按交易数确定抽样步长。
- 每张图最多返回约 1,000 个点，并额外保留最大盈亏和最小盈亏记录，避免极端值被抽样遗漏。
- 抽样步长随结果量自适应，小数据集保持逐笔坐标，大数据集不再把全量坐标回传浏览器。

### 2.4 缓存

- 汇总、分组和总览对象使用 30 秒短 TTL 用户级缓存。
- 交易同步、账户重置、账户删除、账户导入和账户配置更新后统一清除该用户的缓存。
- 缓存只减少重复筛选请求，不替代 SQL 聚合和数据库投影表。

## 4. 性能结果

以下为稳定后端进程下的接口实测值：

| 接口 | 优化前 | 最终冷路径 | 最终热路径 | 响应体积 |
|---|---:|---:|---:|---:|
| `/summary` | 约 1.709s | 约 0.518s | 约 0.018s | 34.5KB |
| `/groups?view=day&limit=8` | 约 0.258s | 约 0.376s | 约 0.39s（接口层复核） | 260KB |
| `/overview` | 约 3.3s | 约 1.37s | 约 0.017s | 816KB |

结论：

- 总览冷路径从约 3.3 秒降到约 1.37 秒，且不再把 12.7 万笔轻量交易构造到 Python 内存。
- 汇总冷路径从约 1.7 秒降到约 0.52 秒，热路径稳定在约 18 毫秒。
- 总览热缓存稳定在约 17 毫秒。
- 分组接口当前主要耗时来自返回 8 个高密度交易日的完整明细，不再是全量统计聚合；缓存收益受响应体大小和框架序列化影响，后续继续专项评估。

## 7. 残余风险

- `/overview` 冷路径仍需约 1.37 秒，适合继续评估更固定粒度的像素桶聚合。
- `/overview` 响应约 816KB，主要来自累计曲线和三张散点图的坐标数据。
- `/groups` 在 8 个高密度交易日下响应约 260KB，接口层缓存收益不显著，后续应评估字段裁剪或按需返回表格列。
- 当前缓存为单进程内存缓存，多实例部署时需要替换为 Redis 或带版本号的共享缓存。

## 8. 结论

`PERF-001` 的主体目标已经完成：汇总、分组键和总览统计不再依赖浏览器全量交易，筛选变化不会重复执行 Python 全量聚合，真实数据口径对照和完整浏览器回归均通过。后续只需继续做响应体积和真正像素桶粒度的优化，不再阻塞交易记录与交易总览的正常使用。
