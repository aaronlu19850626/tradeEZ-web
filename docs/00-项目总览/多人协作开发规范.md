# 多人协作开发规范

版本：2.0；状态：已生效；用途：支持单人多任务、多模型和多人多模块协作；维护人：集成负责人；依赖：《Git分支与PR规范》《新工作启动操作手册》；验收入口：独立 worktree/环境、明确目录归属和通过门禁的 PR。

## 1. 协作单元与角色

一个可验收交付单元对应一个 Issue、分支、worktree、主要 AI 任务和 PR。大模块拆成有明确依赖的子 Issue；不把一个庞大模块长期锁在一个不可审查的 PR，也不让两个独立任务同时写同一工作目录。

产品负责人确认需求与 Mock；模块负责人负责实现和证据；审查人做技术审查；集成负责人管理共享资源、迁移链和合并。单人可以兼任角色，仍须留下不同阶段的确认记录。CODEOWNERS 是审查路由，不能替代 Issue 的任务认领。

GitHub main 是已合并代码事实源，Issue 是任务状态事实源，PR 是实现和验证事实源。分支保护、必需检查、审查人数以 GitHub 实际设置为准；期望开启不等于已配置。

## 2. 本轮基线与后续任务的区别

用户明确要求此前未提交代码进入 main，本轮先保留、分类、核查和归并，不从旧 main 重建覆盖。该例外仅用于本次基线整理；后续功能/文档均走 Issue 和 PR，不能据此直接推 main。

Notebook、笔记历史、笔记模板重新研究，旧方案已失效，通用编辑器代码保留。当前先全面盘点 TradeZella，再确认一期大模块范围、依赖和优先级；旧迁移号段、旧阶段顺序和草案不能自动变为任务分配。

## 3. 任务登记和目录归属

开始前由负责人在 Issue/模块卡片登记：

| 项目 | 必填内容 |
|---|---|
| 身份与范围 | 负责人、审查人、目标、明确不做、当前阶段 |
| 代码 | 分支、worktree、main 基准提交、允许修改的前后端/测试目录 |
| 依赖 | 被依赖 Issue/PR、已冻结契约、共享组件依赖 |
| 环境 | 开发/E2E 端口、dev/test/e2e 数据库名称、合成数据版本 |
| 共享资源 | 需要改的文件、占用人、预计释放条件、关联 PR |
| 交付 | 功能矩阵、确认记录、测试、回滚点、下一步 |

目录以仓库真实路径为准，不为未开发模块虚构 `backend/app/<module>/` 或迁移号段。模块可以在互不依赖时并行研究和 Mock；只有自己的未通过阶段被阻止继续，不能因一个模块尚在测试而冻结所有团队工作。

## 4. worktree 与独立环境

```bash
git fetch origin
git worktree add ../wt-example-123 -b feat/example-123 origin/main
```

一台机器不同任务使用独立 worktree、依赖目录、端口、数据库、环境变量文件、Playwright 状态和报告。不同机器遵守同样登记；开发者名称不能替代任务标识，因为同一人可并行多个任务。

- dev 库：`tradeez_dev_<owner>_<task>`。
- pytest 库：`tradeez_test_<owner>_<task>`，明确设置 `TRADESYNC_TEST_DATABASE_URL`。
- E2E 库：`tradeez_e2e_<owner>_<task>`，明确设置 `TRADEEZ_E2E_DATABASE_URL`。
- E2E 地址：独立 `TRADEEZ_BASE_URL` 和带 `/api/v1/` 的 `TRADEEZ_API_URL`。
- 配置从模板生成；认证状态和数据不共享。测试不得回退使用 dev/生产库，也不得跳过数据库错误冒充通过。

可共用本地 PostgreSQL 进程，不可共用任务数据库。完整安装/启动/播种命令以《新工作启动操作手册》为准。

## 5. 共享文件和串行资源

下列资源必须先在 Issue 登记占用，由集成负责人协调后修改：

| 资源 | 合并规则 |
|---|---|
| `backend/app/migrations.py`、`backend/migrations/versions/` | 单链、中央串行分配下一 revision |
| package.json / package-lock.json / requirements | 依赖改动优先独立小 PR；其他分支 rebase 后重新安装 |
| 全局导航、权限入口、Token、基础组件 | 先确认跨模块影响，共享改动先合并，模块分支随后同步 |
| 共享 API/类型/业务组件 | 契约先评审，兼容性与消费者回归随 PR |
| AGENTS、文档索引、项目进度、CI | 集成负责人协调，小范围追加或准确替换，不重写他人记录 |

模块内发现需要共享能力时，先复用或提出共享 PR；不能复制一份 Button/Dialog/Table 来绕过协作。一个任务完成后在 Issue 明确释放资源，不靠口头“我改完了”。

### 迁移单链

1. 需求和 Mock 确认后提出迁移申请；申请列数据变更、兼容/回滚限制和依赖，不抢占号段。
2. 集成负责人根据最新 main 的链尾串行分配下一 revision。任一时刻只允许一个集成中的迁移 PR 改单链。
3. 同时更新现有框架需要的 `_MIGRATION_STEPS`、`SCHEMA_VERSION`、Alembic revision/down_revision；隔离库验证新建与升级。
4. 迁移 PR 合并后，下一个迁移分支 rebase 后重新核对链尾；已发布 revision 不修改，只新增修正。
5. 迁移不可逆时记录恢复备份/前向修复方案；不对共享/生产库执行测试性 drop 或重置。

## 6. 提交、审查和冲突

开发者按阶段提交可审查改动，需求和 Mock 未确认前不越级实现后端。合并前 fetch/rebase 最新 origin/main，运行 `scripts/quality/static.sh`，涉及页面时运行 `scripts/quality/e2e.sh`；PR 附确认、研究和当前提交证据，CI 通过后由集成负责人合并。

冲突按语义和归属解决，不直接“只留自己代码”、丢弃锁文件或全选 ours/theirs。锁文件先统一 package.json 意图再由 npm 生成；迁移按单链重新分配；全局组件要验证所有消费者。不能安全解决时 abort rebase，记录具体阻塞文件并请对应负责人协作。

分支只由任务负责人更新；已推送后 rebase 需要确认没有共写再使用 `--force-with-lease`。不要对别人的分支或 main force push。

## 7. 中断、收尾与培训

每次暂停/换人使用《开发交接指南》的最小交接包，记录实际 HEAD、未提交归属、阶段确认、测试与下一步。合并后同步项目摘要、关闭 Issue、清理已停止且干净的 worktree，人工处理专用库和临时资源。

培训以一个低风险任务演练完整流程；通过标准是另一人仅凭记录能继续工作。规范不是要求每一步重复询问：已有用户确认继续有效，常规实现与修复由负责人自主推进，只有新产品取舍和新的外部权限需要补充决定。
