# 开发交接指南

版本：2.0；状态：已生效；用途：切换开发人员、模型或机器时准确恢复任务；维护人：模块负责人；依赖：《新工作启动操作手册》《Git分支与PR规范》；验收入口：接手者核对 Git、运行隔离环境并复现一项验收证据。

## 1. 交接事实的优先级

- 用户最新明确决定和相应确认记录决定产品范围；GitHub `main` 是合并代码事实源。
- Issue/模块卡片记录阶段、边界、负责人、阻塞和确认；PR/提交记录实现与测试。未提交文件仍需保留并说明来源，不能因为不在主干就丢弃。
- 项目进度只作摘要，测试结果只证明执行时的那个提交。聊天摘要和归档文档不能覆盖当前代码与确认记录。
- 本轮原未提交成果进入 main 是用户授权的基线整理例外；后续回归 PR 流程。
- Notebook、笔记历史、笔记模板需求重新研究，旧文档无约束力；编辑器代码保留可评估。一期先全面研究 TradeZella，后评审方向和大模块计划，草案不构成开工授权。

## 2. 交出任务前

1. 核对 `git status --short --branch`、`git log -1 --oneline` 和 `git worktree list`；列出未提交文件及所属任务。
2. 尽量形成可理解的阶段提交；不为“工作树干净”提交密钥、日志、数据或坏构建。不便提交的改动保留在原 worktree，并写清接续方式。
3. 更新 Issue 与模块卡片；有远程发布授权时同步远程分支。无法访问 GitHub时保留本地交接文档并注明待同步，不能伪造 Issue/PR URL。
4. 记录数据库名称、端口、迁移状态、运行进程和共享资源占用，不记录 URL、口令、Cookie、认证状态或个人数据。
5. 写出下一步具体到命令/文件/验收用例的动作，以及已获得的授权，避免接手者重复询问或越过未确认门禁。

交接模板：

```text
目标 / 不做范围：
Issue / PR / 模块文档版本：
当前负责人 / 接手人 / 时间：
分支 / HEAD / main 基准 / worktree：
阶段 / 最近需求确认 / 最近 Mock 确认：
已完成及证据链接：
未完成 / 未提交文件及归属：
测试命令 / 执行提交 / 结果 / 未执行项：
依赖与共享资源占用 / 迁移 revision：
本地端口、数据库名称（无敏感值）：
阻塞 / 风险 / 未决产品选择：
下一步：
回滚点与恢复限制：
```

## 3. 接手者操作

```bash
git rev-parse --show-toplevel
git status --short --branch
git worktree list
git log -5 --oneline
git remote -v
```

阅读 AGENTS.md → 当前接手快照 → 本文 → 新工作启动操作手册 → 文档索引/项目进度 → 当前 Issue/PR/模块卡片。核实分支、HEAD、实际改动和确认版本；不一致时先说明差异，不执行 reset/clean。原任务继续使用原 worktree；需要隔离新的任务则从最新 `origin/main` 建新分支，不复制别人的 `.env` 或认证文件。

按操作手册重建独立依赖和 dev/test/e2e 三库，加载自己的任务配置。运行 `scripts/quality/static.sh`；有页面改动时运行 `scripts/quality/e2e.sh`。只有部分验证时逐项列明，不宣称全量通过。接手人复现至少一个关键场景，并在 Issue 写下接手时间、当前阶段、第一项动作与共享资源占用。

给新 AI 的指令：

> 请先阅读 AGENTS.md 与当前接手快照，再核对交接记录和实际仓库，不重复已完成工作。列出实际分支/HEAD、未提交文件、运行状态、最近确认点和尚缺证据。保持原成果，从交接下一步继续；不得把 Notebook 归档或一期草案当已确认需求。只在新的产品决策或权限确实缺失时提问。

## 4. 发布、密钥与数据库的边界

开发交接不传生产环境、生产数据库副本或真实密钥。迁移运行前核对环境；test/e2e 库必须符合专用前缀，门禁失败先修配置。确需生产运维时建立独立授权任务，由环境负责人通过安全渠道处理加密密钥与备份，不把运维凭据混入研发交接。

完成后检查：接手者能定位下一步、复现验证、明确未决项；旧负责人释放共享资源；Issue、PR、文档与实际 Git 一致。
