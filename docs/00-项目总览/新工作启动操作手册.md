# 新工作启动操作手册

版本：2.0；状态：已生效；用途：培训开发人员并指导 AI 从主干到验收的每一步操作；维护人：项目负责人/集成负责人；依赖：《开发机制总览》《Git分支与PR规范》《质量门禁与并行运行规范》；验收入口：新成员完成一次隔离环境演练，并提交具有阶段证据的 PR。

## 1. 先分清现在要做什么

当前先全面盘点 TradeZella 核心模块，再与产品负责人确定一期方向、范围和优先级。《一期方向与大模块开发计划》是研究与讨论草案，不是已确认排期；盘点不能自行转为业务开发。

Notebook、笔记历史、笔记模板的旧需求和验收状态已重置，归档只用于追溯。已有编辑器代码保留为待评估的工程资产，不代表新 Notebook 必须采用旧接口或旧产品行为。

本次主干整理有用户明确授权：把之前未提交的代码成果保留并纳入主干，不能用旧 `origin/main` 覆盖这些代码。这是一次基线整理例外；后续工作均走 Issue → 分支/worktree → PR → 门禁 → 审查 → 合并。

角色可以由同一人承担，但记录中必须区分：产品负责人确认范围与 Mock；模块负责人交付实现；集成负责人管理共享资源和合并；审查人独立核对证据。

## 2. 接手前的检查与 AI 首条指令

打开包含 `.git`、`AGENTS.md`、`frontend/`、`backend/` 的实际仓库根目录。本机是 `tradeEZ-web/github-src/`；其他机器以 `git rev-parse --show-toplevel` 为准。不要在外层历史 `frontend/` 开发。

```bash
git rev-parse --show-toplevel
git status --short --branch
git remote -v
git worktree list
git log -5 --oneline
gh auth status
```

依次阅读 `AGENTS.md`、文档索引、开发机制总览、项目进度、一期研究草案、当前 Issue 和模块卡片，再读取全局样式/UI 规范及相关代码。不要把聊天摘要、旧文档的“通过”当作当前提交的测试结果。

可直接发给 AI：

> 先读取 AGENTS.md 与新工作启动操作手册，仅做现状核查。报告仓库根目录、分支、工作树、未提交改动、目标 Issue、当前阶段、允许修改目录、共享资源和本次第一步。已有改动必须保留；一期尚待 TradeZella 全面研究后确认，不能自行选定模块开始开发。不要输出 .env、Token 或认证状态的内容。

若有未提交改动，先说明归属并由原任务提交或留在原 worktree；不执行 `reset --hard`、`clean -fd` 或直接覆盖文件。只有已经授权的本轮基线整理可以按保留清单统一归并。

## 3. 建立 Issue 和模块卡片

产品研究任务可以先建研究 Issue；正式模块开发必须等待一期范围确认。一个可验收交付单元对应一个 Issue、分支、主要 worktree 和 PR。大模块过大时在同一模块总 Issue 下拆分子 Issue，每个子任务单独走流程。

GitHub 网页可选择仓库 Issue 模板。CLI 示例先准备正文文件，再创建 Issue：

```bash
cat > /tmp/tradeez-module-issue.md <<'EOF'
目标：
用户与使用场景：
本次包含 / 不包含：
当前阶段：研究
模块负责人 / 审查人 / 集成负责人：
允许修改目录：
共享资源申请：
依赖模块与接口：
功能点矩阵和验收用例：
研究证据目录：
需要产品确认：范围、前端 Mock 和数据逻辑
阻塞 / 风险 / 回滚点：
EOF
# 先编辑补全正文，再运行；模块名必须来自已确认范围。
gh issue create --title '[模块] <模块名与目标>' --body-file /tmp/tradeez-module-issue.md --assignee @me
```

复制《模块开发卡片模板》和《功能点覆盖矩阵模板》到当前模块文档，填写实际 Issue URL，并在文档索引登记。不要把示例尖括号当实际命名。记录模块负责人、目录、分支、worktree、端口、三个数据库名称；数据库 URL 和密钥不写 Issue。迁移只登记“是否需要”和“串行申请状态”，不预分配固定号段。

给 AI：

> 当前 Issue 是 <链接>，阶段为研究。请盘点现有路由、组件、API、数据表、权限和测试；补齐模块卡片及功能点矩阵草稿。只研究与编写文档，不实现新业务、不创建迁移。发现不可从代码推导的产品决策时给出选项与建议。

## 4. 从最新主干创建隔离 worktree

下面用 `example-123` 表示已登记的模块和 Issue 编号，使用前替换一次。由仓库根目录执行；GitHub 登录和远端访问应已配置好。

```bash
git fetch origin
git worktree add ../wt-example-123 -b feat/example-123 origin/main
cd ../wt-example-123
git status --short --branch
git log -1 --oneline
```

不必切换或清理当前主 worktree。已存在的任务从自己的 worktree 继续，不重复建分支。每个 AI 任务打开对应 worktree 的根目录；允许子代理在同一任务中按互不重叠文件协作，但不得让独立任务共写该目录。

把实际分支、worktree、基准提交、负责人和目录边界追加到 Issue。没有获得共享文件的编辑权时，先实现模块内内容，另开共享变更依赖任务。

## 5. 为每个任务准备独立环境

准备 Git、GitHub CLI、Node.js 22、npm、Python 3.11+ 和 PostgreSQL 16。安装版本以仓库 CI/依赖文件为准，安装新包前必须先申请依赖串行资源。

每个 worktree 使用独立 `.venv`、`node_modules`、`.next`、Playwright 状态和报告；不复制别人的依赖目录或认证文件。单机任务可以共用 PostgreSQL 进程，但必须使用独立数据库和端口登记。以下是本地 Docker 示例；已有本地 PostgreSQL 时可用等价 `createdb` 命令，不重复启动服务。

```bash
# 每个任务更换名称和端口；下述口令仅用于绑定回环地址的本地演练。
docker run --name tradeez-pg-example-123 -d \
  -e POSTGRES_USER=tradeez \
  -e POSTGRES_PASSWORD=local-example-123 \
  -p 127.0.0.1:55411:5432 postgres:16
# 确认返回 accepting connections 后继续。
docker exec tradeez-pg-example-123 pg_isready -U tradeez

docker exec tradeez-pg-example-123 createdb -U tradeez tradeez_dev_example_123
docker exec tradeez-pg-example-123 createdb -U tradeez tradeez_test_example_123
docker exec tradeez-pg-example-123 createdb -U tradeez tradeez_e2e_example_123
```

数据库分工：`tradeez_dev_*` 保存本任务手工开发数据；`tradeez_test_*` 仅用于可重建的 pytest 数据；`tradeez_e2e_*` 仅用于浏览器合成数据。测试不得回退到开发/共享/生产库；test/e2e 名称前缀由门禁校验。不同并行测试任务也不能复用同一 test/e2e 库。

安装依赖和本地配置：

```bash
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt -r backend/requirements-dev.txt
# 仅首次创建；已经存在的配置先保留并核对，不覆盖。
cp -n backend/.env.example backend/.env
cp -n frontend/.env.local.example frontend/.env.local
cd frontend
npm ci
npx playwright install chromium
cd ..
```

用编辑器修改 `backend/.env`：数据库为该任务的 `tradeez_dev_*`；`TRADESYNC_ENVIRONMENT=development`；本地演练设 `TRADESYNC_AUTH_TEST_MODE=true`；生成不同的随机 `TRADESYNC_AUTH_SECRET` 和 `TRADESYNC_SYNC_KEY_ENCRYPTION_SECRET`，不使用生产密钥。可以在本机运行 `openssl rand -hex 32` 生成，但不把结果贴入聊天、Issue 或提交。验证码测试模式不可用于部署。

在 worktree 根目录创建被忽略的 `.env.task`；示例中的名称/端口按登记替换，真实远程密码不要写进示例文档：

```dotenv
TRADESYNC_DATABASE_URL=postgresql://tradeez:local-example-123@127.0.0.1:55411/tradeez_dev_example_123
TRADESYNC_TEST_DATABASE_URL=postgresql://tradeez:local-example-123@127.0.0.1:55411/tradeez_test_example_123
TRADEEZ_E2E_DATABASE_URL=postgresql://tradeez:local-example-123@127.0.0.1:55411/tradeez_e2e_example_123
TRADEEZ_BACKEND_PORT=8111
TRADEEZ_FRONTEND_PORT=3111
TRADEEZ_BASE_URL=http://127.0.0.1:3311
TRADEEZ_API_URL=http://127.0.0.1:8311/api/v1/
```

`TRADEEZ_BASE_URL` 和 `TRADEEZ_API_URL` 是此任务受管 E2E 服务的地址，使用与开发服务不同的端口。手工开发前端的 `frontend/.env.local` 中 `NEXT_PUBLIC_API_BASE_URL` 和 `NEXT_PUBLIC_EA_API_BASE_URL` 则都指向 `http://127.0.0.1:8111/api/v1`。本机端口须在 Issue 登记且不重复占用。

每个新终端进入 worktree 根目录后加载任务配置：

```bash
set -a
source .env.task
set +a
git check-ignore backend/.env frontend/.env.local .env.task
```

上条必须输出三个被忽略的路径；若没有，修正忽略规则后再继续，不能 `git add -f` 提交配置。Windows 可使用 WSL 执行本文命令；原生 PowerShell 使用 `.venv\Scripts\python.exe` 并逐个设置等价环境变量。

开发后端终端：

```bash
cd backend
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port "$TRADEEZ_BACKEND_PORT"
```

开发前端另一个终端（重新加载 `.env.task`）：

```bash
cd frontend
npm run dev -- --hostname 127.0.0.1 --port "$TRADEEZ_FRONTEND_PORT"
```

在第三终端检查 `curl -fsS http://127.0.0.1:8111/readyz`，浏览器打开 `http://127.0.0.1:3111/auth/v2/login`。启动后端可能自动升级数据库，所以启动前必须确认所指库名称；不输出完整数据库 URL 作为证据。

## 6. 研究、确认与实现：逐阶段操作

### 阶段 A：参考产品研究

给 AI：

> 按 Issue 功能点，使用专用研究浏览器/Playwright 实际观察 TradeZella。记录页面路径、语言、主题、视口、操作步骤、截图、DOM/CSS 与状态变化。分开标注“观察事实、用户要求、TradeEZ 自主设计、待确认”，不得把猜测写成参考产品事实。先完成核心模块总盘点，再输出用于一期评审的功能地图，不开始编码。

具体操作：从模块首页逐项进入列表、详情、弹窗、菜单和关键状态；每个功能点绑定编号。证据存入 `docs/30-模块设计/research/<module>/`，截图去除账号/真实数据，认证文件仅保留在被忽略的本地目录。观察不到的异常或收费能力标记“未观察”，不要编造；替代交互进入《前端自主设计清单》。

输出功能矩阵：编号、功能、来源、P0/P1/P2 候选、页面/数据行为、是否核心、证据、依赖、验收方式、状态。约 80% 的复刻覆盖率以产品确认的核心清单为分母；未确认、无法观察和待办不能计入已覆盖，用户自定义能力另列，不稀释参考覆盖率。

### 阶段 B：需求范围与方案确认

给 AI：

> 根据已核实证据，提交需求评审稿：用户与目标、一期内外边界、功能矩阵、页面与状态、数据对象和权限、拟议 API 契约、依赖及验收用例。列出需要我选择的产品取舍，不自行沿用 Notebook 旧规则。此阶段只冻结需求，不写后端接口或迁移。

产品负责人确认具体文档版本/提交、功能编号和排除项。将确认内容原文或准确摘要保存到模块卡片，包含日期、确认人、来源链接、文档版本、允许进入的下一阶段。明确一次确认已经覆盖的范围，AI 后续不重复请求；出现影响验收的范围变化才重新评审。

### 阶段 C：前端 Mock

给 AI：

> 范围确认记录为 <链接/版本>。仅实现已确认功能的前端 Mock、状态和数据逻辑，复用全局 Token、shadcn/Radix 及业务组件。Mock 和真实接口适配器共享模块类型；不调用正式业务 API、不新增后端或迁移。完成桌面/平板/移动端、主题及中英文验证后，给我页面、截图、测试和已知差异用于确认。

操作顺序：共享契约类型 → Mock 适配器与确定性数据 → 页面/弹层 → 正常与关键异常状态 → 可访问性与响应式 → 浏览器验证。控件不得为单页需求复制基础库；通用能力提取到共享业务模式并登记设计系统。当前保留现有双主题代码，按 UI 规范验证，不能凭旧固定浅色文档删除主题能力。

运行静态门禁及相关浏览器用例，提交“功能编号→演示入口→结果→证据”；产品确认前端和数据逻辑后才进入后端。不把 Mock 存储当正式持久化，不把研究阶段的临时截图当验收截图。

### 阶段 D：后端与迁移

给 AI：

> Mock 确认记录为 <链接/版本>。实现共享契约对应的权限、服务、接口和隔离数据库验证，保持已确认 UI。先登记迁移串行资源，集成负责人从最新 main 单链末尾分配 revision，不使用旧模块固定号段。报告迁移、权限、并发/幂等、分页搜索和错误恢复的测试证据。

把请求/响应、错误码、分页、所有权、时区/金额和必要的并发规则写入契约。迁移在隔离库验证；遵循现有 `_MIGRATION_STEPS`、`SCHEMA_VERSION` 和 Alembic 单链，已发布迁移只新增修正，不能改写。迁移是否可逆须如实记录，不为通过清单而伪称可回滚。

### 阶段 E：真实联调

给 AI：

> 以已确认 Mock 和 API 契约为准接入真实适配器。验证加载、保存、刷新、筛选分页、重复提交、用户隔离、错误恢复以及模块实际涉及的并发/时区/金额口径。列出发现的问题与证据；本轮范围内缺陷直接修复，新增需求登记 Issue 待评审。

用合成测试账户和数据完成正常流与关键失败流。原模块下线须有替代关系、影响范围和回滚点，并另做回归；不能删除“看起来旧”但仍被引用的服务。

## 7. 质量门禁、提交和 PR

停止本 worktree 的 Next.js 开发服务器后再执行构建，避免 `.next` 产物竞争；其他 worktree 不受影响。加载 `.env.task` 后在仓库根目录运行：

```bash
./scripts/quality/static.sh
./scripts/quality/e2e.sh
git diff --check
git status --short
```

静态门禁包括后端 pytest、TypeScript、Biome、生产构建和差异检查。浏览器门禁自启受管隔离前后端，校验 `tradeez_e2e_` 库并只为新空库播种合成数据；不清理已有数据库。端口被占用、库名不合规或已有库不适用时应修正环境，不能绕过检查。报告应包括执行提交、命令、通过/失败/跳过数量与路径；跳过不等于通过。

提交前人工核对差异，无密钥、`.env`、认证状态、数据库、日志、真实用户截图、构建产物。选择本任务文件暂存，不使用不经检查的 `git add .`：

```bash
git diff --stat
git diff -- <本任务文件路径>
git add -- <本任务文件路径>
git diff --cached --check
git diff --cached --stat
git commit -m 'feat(example): <本次可验收行为>'
git fetch origin
git rebase origin/main
```

若 rebase 发生冲突，按文件归属与依赖解决；不机械选择 ours/theirs。不确定时 `git rebase --abort` 保留原状并登记阻塞。rebase 后针对冲突/新主干影响运行门禁，已发布分支仅可在确认无人共写后使用 `git push --force-with-lease`，不能 `--force`。

推送并建立 PR：

```bash
git push -u origin HEAD
cp .github/pull_request_template.md /tmp/tradeez-pr.md
# 编辑 /tmp/tradeez-pr.md，填写 Closes #123、确认记录、测试和回滚。
gh pr create --base main --title 'feat(example): <可验收目标>' --body-file /tmp/tradeez-pr.md
gh pr checks <PR编号> --watch
```

若用户只让 AI 准备代码而未授权发布，AI 应先准备好正文与差异，再请求具体发布授权；本手册的人工 CLI 操作由任务负责人执行。不得伪造 reviewer 或声称分支保护已启用；是否启用应由集成负责人实际核查 GitHub 设置。

CI 失败先查看具体 job，修复后重跑；不能以本地通过替代失败 CI。需求/Mock 确认由产品负责人完成，技术审查由审查人完成。均满足后集成负责人在 GitHub 合并；建议 squash 合并（保留清晰 PR 记录），不在本地 merge 后直接推 main。

## 8. 合并、收尾和交接

```bash
gh pr view <PR编号> --json state,mergeCommit,url
# 仅在 PR 已合并、worktree 干净且没有运行进程后操作。
git status --short
cd <主仓库根目录>
git fetch origin
git switch main
git pull --ff-only origin main
git worktree remove ../wt-example-123
```

如果主 worktree 有改动或 main 有分叉，停止切换/拉取并核对来源，不强制 reset。squash 后 `git branch -d feat/example-123` 可能拒绝删除；保留也安全，确认 PR 合并且无独有成果后才由负责人删除，不把 `-D` 当日常默认。

Issue 记录合并提交、完成/未完成的验收、后续缺陷；更新项目进度和文档索引。停止任务自己的服务，按约定保留或人工删除专用数据库，禁止按模糊前缀批量清库。环境配置与真实数据不进入交接包。

每次中断、换模型、换人都提交以下交接记录：

```text
Issue / PR：
负责人 / 交接时间：
分支 / HEAD / worktree：
当前阶段 / 最近确认记录：
已完成事实与证据：
未提交文件归属：
最近测试命令、提交、结果及未执行项：
数据环境名称（无 URL/密码）：
共享资源/迁移占用：
阻塞与风险：
下一步唯一明确动作：
回滚点：
```

接手 AI 指令：

## 9. 新成员培训验收

先使用不涉及业务逻辑的小型文档/样式练习任务走完：阅读入口 → 建 Issue → worktree → 三库隔离 → 启动 → 查看现有组件 → 模拟阶段确认 → 门禁 → 差异审查 → PR → CI → 交接。培训者必须观察学员能说明“研究事实和产品决定的区别”“Mock 何时可进入后端”“测试为何不能连接开发库”“哪些文件须串行”“如何在不丢代码时处理冲突”。

验收通过标准：另一人仅凭交接记录能找到正确分支、启动隔离环境、重现一个测试并说清下一步。未完成的步骤写明原因；培训练习不能冒充一期模块验收。
