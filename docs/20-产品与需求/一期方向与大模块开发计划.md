# 一期方向与大模块开发计划

版本：2.0；状态：盘点准备中，未形成排期；用途：先完整盘点 TradeZella 核心模块，再与用户共同确定一期方向、边界和优先级；维护人：项目负责人；依赖：开发机制总览、TradeZella 研究证据规范、功能点覆盖矩阵模板；验收入口：核心模块盘点评审 Issue。

## 1. 已确认的方向

- 当前不沿用旧的一期模块顺序，也不预先指定 Notebook 或其他模块的开发优先级。
- 先全面盘点 TradeZella 核心模块、能力、状态、数据关系和用户路径。
- 完成 TradeZella 盘点后，再对照 TradeEZ 现有代码，识别已完成、部分完成、仅 Mock、缺失和需要重做的能力。
- 用户与技术负责人基于盘点证据共同决定一期范围、模块依赖、开发波次和验收深度。

TradeZella 只作为结构、交互和核心业务能力的参考；TradeEZ 的数据口径、视觉系统、权限和产品取舍由用户确认。

## 2. 盘点对象

盘点至少覆盖账户与数据接入、总览、交易中心、交易详情、报告与统计、策略与 Playbook、复盘与日志、Notebook、回测、AI、设置与权限等核心区域。这个清单只是研究导航，不代表一期承诺或开发顺序。

每个模块必须记录：

- 入口、用户角色、完整操作路径和核心任务。
- 页面、弹层、键盘行为、桌面与移动端状态。
- 加载、空、错误、权限、重复提交和并发等异常状态。
- 数据对象、筛选和统计口径、跨模块依赖。
- 截图、DOM/CSS 数值、观察时间和证据可信度。
- TradeZella 事实、用户要求和 TradeEZ 自主设计的边界。
- 对照当前代码后的实现状态和可复用资产。

## 3. 四个评审阶段

1. **核心模块盘点**：逐模块完成研究证据和能力清单，不在观察阶段排期。
2. **现状差距盘点**：把能力标记为已验收、部分实现、仅 Mock、旧实现待重做或缺失。
3. **优先级评审**：按核心闭环价值、用户价值、依赖、数据成熟度、组件复用、风险和工作量评分。
4. **一期路线确认**：用户确认一期大模块、波次、明确不做项、验收标准和调整机制后，才进入开发。

## 4. 盘点完成的出口

- 核心模块地图和用户路径图完整。
- 每个模块有功能点覆盖矩阵、研究证据和现有代码差距。
- 跨模块数据对象、串行资源和高风险依赖已登记。
- Notebook、笔记历史和笔记模板旧方案只保留在历史归档，不作为新需求输入。
- 形成供用户评审的候选一期组合；评审前任何排列都不是正式排期。
