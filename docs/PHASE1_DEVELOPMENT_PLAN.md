# TradeEZ Web 第一阶段正式开发计划

版本：V1.0  
依据：`PHASE1_FUNCTIONAL_REQUIREMENTS.md`  
日期：2026-09-18  
UI 基线：Studio Admin / `arhamkhnz/next-shadcn-admin-dashboard`（MIT）

## 1. 开发目标与范围

第一阶段建设一个面向个人交易者的正式 Web 控制台，完成：

1. MT5 EA 数据同步、账号接入、同步日志、重同步与账号删除。
2. 原始成交/订单可核对，完整交易 Trade 可复盘。
3. 标签、Setup、Playbook、规则版本、执行评分。
4. 单笔复盘、截图、笔记、情绪、错误和改进行动。
5. 整体交易分析、模型/时间/错误/执行/标签分析。
6. 盘前计划、交易意图、盘后总结、周复盘、习惯与站内待办。
7. 使用 Studio Admin 的 Next.js + shadcn/ui 管理后台界面。

不做自动下单、复制交易、强制阻止 EA 开仓、实时风控、行情回放、自动回测、AI 自动复盘或公开社区。

## 2. 必须保留的现有能力

以下 EA 同步接口已经上线，第一阶段继续保留，不做破坏性修改：

| 接口 | 现状 | 兼容要求 |
|---|---|---|
| `POST /api/v1/sync/last_sync_time` | 查询游标 | 保留请求/响应；字段仍按 UTC 秒 |
| `POST /api/v1/ingest/deals` | 上传成交，HMAC，幂等 upsert | 保留；新增字段只能追加，不能要求 EA 立即升级 |
| `POST /api/v1/sync/update_last_sync_time` | 两阶段提交游标 | 保留；同步轮次治理围绕它增强 |
| `POST /api/v1/ingest/symbols` | 品种规格 | 保留 |
| `POST /api/v1/ingest/snapshots` | 账户快照 | 保留 |
| `POST /api/v1/ingest/settings` | EA 参数快照 | 保留并升级为按实例/版本查看 |
| `POST /api/v1/ingest/heartbeat` | 心跳、时区、券商信息 | 保留；增加实例标识等兼容字段 |
| 邮箱验证码登录 | 已实现 | 迁移到正式前端，认证机制保留 |
| 账号绑定/重置 Key | 已实现 | 保留 Key 生成、加密、HMAC、只展示一次原则 |

旧控制台 `backend/app/dashboard.html` 在新前端达到功能对等前继续保留，可通过 `/dashboard?legacy=1` 访问；新前端成为默认入口。

## 3. 当前能力差距

### 已具备

- FastAPI 服务、SQLite 数据库、邮箱验证码登录。
- MT5 账号、同步 Key、心跳、成交、品种、快照、EA 参数。
- v2.1 UTC 游标、HMAC、成交幂等和独立游标提交。
- 临时完整交易配对接口和简易数据控制台。
- API 审计日志基础表。

### 主要缺口

- 账号缺少必填同步开始日期、服务器必填校验、停用/恢复、同步轮次、清空重同步、物理删除。
- 当前“完整交易”是接口内临时配对，没有落库的 Trade 生命周期、待核对状态和归并问题。
- 原始成交查询、跨账号筛选、全字段详情、服务端排序和分页不足。
- 同步日志不能记录同步轮次、订单号/成交号清单，也缺少新增/更新/重复/失败的严格口径。
- 标签、Setup、Playbook、规则版本、评分、复盘、附件均未建域模型。
- 分析、每日计划、意图、日总结、周复盘、行动、习惯和待办尚未实现。
- 前端仍是单 HTML，不是 Studio Admin 正式工程。
- 缺少正式数据库迁移、测试夹具、接口契约测试、E2E 验收和部署文档。

## 4. 总体技术方案

### 4.1 工程结构

- 后端继续使用 FastAPI，重构为模块化单体：`accounts / sync / trades / tags / playbooks / reviews / analytics / planning / habits / attachments`。
- 前端在 `frontend/` 引入 Studio Admin，使用 Next.js 16 App Router、TypeScript、Tailwind CSS v4、shadcn/ui、TanStack Table、React Hook Form、Zod、Recharts、FullCalendar、Vaul。
- EA 不直接访问前端服务；FastAPI 仍是唯一系统记录源。Next.js 负责 BFF、页面、表格和文件上传入口。
- 第一阶段继续使用 SQLite，但通过 Alembic 管理表结构，并把 SQL 收敛到 repository 层；生产多实例或公网化时切换 PostgreSQL。
- 附件使用本地私有对象存储：文件落盘，数据库存元数据，访问走鉴权接口；后续可替换 S3/MinIO。

### 4.2 时间、币种与事实口径

- 事实时间全部存 UTC 秒或 UTC ISO；展示时区和交易日分界属于工作区配置。
- MT5 服务器时区只用于展示，不参与 UTC 转换。
- 默认北京时间、00:00 日切；伦敦/纽约时段使用 IANA 时区和夏令时规则。
- 多币种金额分币种统计，第一阶段不做自动汇率换算。
- EA 事实、系统计算、规则判断、用户手填、事后补录必须有来源标识。
- 原始成交事实只读，不允许用笔记直接覆盖；人工修正保留原值、新值、原因、时间和操作人。

## 5. 数据域建设计划

### 账号与同步

- 扩展 `accounts`：服务器名、显示名称、同步起点、账号状态、展示币种、当前同步轮次、停用时间、删除物理清理标记。
- 唯一约束：同一用户下 `mt5_login + broker_server` 不可重复。
- 新增 `ea_instances`：EA 名称、版本、实例标识、心跳时间、服务器时区、运行参数。
- 新增 `sync_runs / sync_batches / sync_batch_refs`：记录同步轮次、批次、游标、接收/新增/更新/重复/失败数量及订单号、成交号、持仓号。
- 日志允许保存标识号，不保存价格、手数、盈亏、Key、Token、验证码等敏感明细。
- 同步轮次号用于拒绝旧请求回写；清空重同步时必须使旧轮次失效。

### 原始事实与完整交易

- 保留 `deals` 为不可变原始成交表，新增原始订单表以接收 EA 后续提供的订单事实。
- 新增 `trades`：完整交易主表，状态为未结束、已结束、待核对、数据待恢复、范围外。
- 新增 `trade_members`：开仓、加仓、部分平仓、反向/反转等成交关联及数量、方向、归并依据。
- 新增 `trade_issues`：缺开仓、数量不平、缺费用、跨起点、关联冲突、净持仓反转不确定等问题。
- 新增 `fact_corrections`：系统计算字段可人工纠正，原始事实不改写。
- 新增 `trade_risks`：初始风险金额必须来源可追溯；没有有效风险时不计算 R。
- 完整交易构建器替代当前临时 `pair_positions()`，输出可解释归并结果；无法唯一归并不得强行合并。

### 标签、模型与规则

- `tag_groups / tags / trade_tags / tag_merge_audit`：支持单选/多选、停用、合并、冲突处理、主要错误。
- `setups`：交易机会模型，可启用/停用，内置模板必须复制后才能成为用户规则。
- `playbooks / playbook_versions / rules / rule_versions`：草稿、发布、停用、不可变版本。
- 规则支持是非、数值、选项、文本；人工和确定性自动评估分开；关键规则、权重、检查时点、N/A 条件显式配置。
- `review_evaluations` 引用当时发布版本，规则更新不重写历史评价。

### 复盘与附件

- `trade_reviews / review_versions`：待复盘、草稿、已完成、待重新核对；使用版本号或时间戳处理并发编辑。
- `review_notes`：盘前、盘中、盘后笔记，系统创建时间和用户声称事件时间分开，事后补录有标记。
- `attachments`：盘前、入场、退出、复盘分类，标题、说明、周期、排序、替换、删除。
- 结构化情绪、错误标签、复盘结论、下次行动；截图不作为所有交易的强制项。

### 分析与每日闭环

- 建立统一筛选对象：账号、日期口径、品种、方向、模型、规则版本、时段、标签、复盘状态、规则结论、币种。
- 分析结果按完整交易、已实现日账、有效 R 子集分别返回样本数和排除原因。
- `day_plans / plan_scenarios / plan_revisions`：准备交易、仅观察、休息；计划确认和修订保留版本时间。
- `intentions / intention_events`：观察、准备执行、待关联、已关联、放弃、失效、到期。
- `daily_reviews / weekly_reviews / improvement_actions / action_events`：日总结、周复盘、行动状态和效果验证。
- `workspace_settings / trading_schedules / reminders / habit_snapshots`：交易日、提醒、站内待办、按时/补录统计。
- `export_jobs`：导出当前页或全部筛选结果，记录范围、币种、时间口径和生成时间。

## 6. 前端信息架构与 Studio Admin 路由

### 6.1 采用原则

- 完整引入 Studio Admin（`next-shadcn-admin-dashboard`）的工程结构、主题、侧边导航、顶部栏、表单、表格、抽屉、弹窗和数据展示风格。
- 品牌、菜单名称和业务页面按 TradeEZ 调整；不绕过其设计体系另起一套页面。
- 页面以“数据显示和复盘操作”为中心，账号绑定与 EA 配置属于低频操作，只在首次接入或需要修改时通过抽屉完成。
- 危险操作、详情查看、批量操作优先使用右侧抽屉或对话框；用户不需要离开列表即可完成核对。
- 所有关键状态同时使用文字和颜色表达；移动端保留核心指标、待办和抽屉操作。

### 6.3 关键页面布局

1. **今日工作台**：顶部显示交易日、北京时间/本地时间、MT5 服务器时区；下方为计划状态卡、当日统计、意图时间线、待复盘交易和日总结入口。
2. **交易日志**：默认显示有效已结束 Trade；表格列包括交易号、账号、品种、方向、数量、开仓时间、平仓时间、持仓时长（秒）、止损、止盈、库存费、佣金、净盈亏、币种、模型、规则结论、复盘状态。
3. **原始订单**：默认平仓时间倒序，支持跨账号；排序在全量筛选结果上生效，并以原始记录 ID 作为最终稳定排序字段。
4. **交易详情抽屉/页面**：上部为事实与完整性状态，中部为成交成员和费用，下部为标签、计划/意图关联、规则评分、笔记、截图和复盘结论。
5. **账号绑定抽屉**：添加账号时只填写一次账号、服务器、同步起点、显示名称和备注；成功后集中展示服务器 Key、EA 接入参数和复制按钮，Key 关闭后不再完整显示。
6. **分析页**：所有图表必须带样本数、币种、口径和排除原因；点击图表下钻时保留筛选条件并可返回原分析。
7. **规则页**：用版本化编辑器和发布确认，禁止直接编辑已发布规则；历史评价显示当时版本号。
8. **日历页**：使用 FullCalendar 展示日账与流程状态，无数据、同步中、零盈亏和不交易日使用不同文案。

### 6.4 前端共享能力

- API client、JWT 刷新/过期处理、Zod 响应校验、TanStack Query 数据状态和 TanStack Table 列表能力统一封装。
- 建立 `DataTable / FilterBar / MetricCard / StatusBadge / TradeDrawer / ReviewForm / RuleMatrix / PlanTimeline / AttachmentUploader / ImpactConfirmDialog / EmptyState` 等共享组件。
- 长文本表单自动保存草稿；保存失败保留输入，显示真实重试状态。
- 列表列宽、列顺序、显示列和常用筛选按用户偏好保存。
- 金额、时间、持仓时长、R、时区和币种使用统一格式化器；金额永远带币种，持仓时长可显示友好文本但原始精度到秒。
- 文件上传支持失败重试，单张图片失败不覆盖其他复盘字段。
- 所有用户输入按文本渲染，防止 XSS；外链和附件预览均经过鉴权。

## 7. 服务端接口与兼容策略

### 7.1 API 分区

| 分区 | 前缀 | 使用方 | 策略 |
|---|---|---|---|
| EA 同步 API | `/api/v1` | MT5 EA | 已上线接口保持请求/响应兼容，新增字段只追加、不强制升级 |
| Web 正式 API | `/api/v1/web` | Studio Admin 前端 | 新建正式业务接口，统一鉴权、分页、筛选、错误格式 |
| 内部兼容 API | `/internal/legacy/*` | 旧测试脚本/旧页面 | 保留到新控制台验收完成，再评估下线 |
| 健康检查 | `/healthz`、`/readyz` | 本机/局域网运维 | 不返回敏感配置、Key、订单数据 |

EA 不直接连接 Next.js；Next.js 通过服务端 Route Handler 或 BFF 调用 FastAPI，浏览器不保存 EA HMAC Key。

### 7.2 必须保留的 EA 接口

- `POST /api/v1/sync/last_sync_time`
- `POST /api/v1/ingest/deals`
- `POST /api/v1/sync/update_last_sync_time`
- `POST /api/v1/ingest/symbols`
- `POST /api/v1/ingest/snapshots`
- `POST /api/v1/ingest/settings`
- `POST /api/v1/ingest/heartbeat`

兼容要求：

1. 时间继续使用 UTC Unix 秒；新增 ISO 字段只能作为辅助展示。
2. Bearer Key 和 HMAC-SHA256 校验方式不变。
3. Deal 继续按账号和 ticket 幂等 upsert，重复批次不能制造重复成交。
4. 成交上传与游标提交仍为两阶段，不能因 EA 上传成功就自动认为轮次完成。
5. 旧字段含义不变；新字段使用默认值和可空策略，旧 EA 不需要立即升级。
6. 账号停用、删除、重同步旧轮次、签名错误、时间窗口异常和重复请求必须返回明确错误码。

### 7.3 同步握手与批次确认

在不破坏现有两步同步的前提下增加轮次和批次语义：

1. EA 调用 `last_sync_time`，服务端返回账号状态、当前 `sync_run_id`、游标、协议能力和最低兼容版本。
2. EA 上传数据时可携带 `batch_id`、`batch_index`、`batch_count`、`instance_id`、`protocol_version` 和请求哈希。
3. 服务端在同一数据库事务内完成事实写入、批次引用记录和计数，返回 `accepted / inserted / updated / duplicated / rejected / pending_cursor`。
4. 每个批次响应都包含服务端批次 ID、校验状态和下一次重试建议；EA 可用同一 `batch_id` 安全重试。
5. EA 调用 `update_last_sync_time` 时提交本轮全部批次摘要；服务端核对批次数量、哈希和引用后才推进游标。
6. 若有批次缺失、账号处于重同步中或轮次已失效，游标不推进，并返回缺失批次与可恢复动作。
7. “无新增交易”的成功握手可以更新最近成功时间，但只记录轮次状态，不生成虚假新增业务日志。
8. 日志保存核心请求元数据、批次号、订单号/成交号标识和数量，不保存价格、手数、盈亏、止损、止盈、Key 或签名内容。

后续可追加但不强制当前 EA 升级的接口：`/api/v1/ingest/orders`、`/api/v1/ingest/positions`、`/api/v1/ingest/risks`、`/api/v1/sync/ack`。

### 7.4 Web API 资源规划

- **认证与用户**：发送验证码、验证码登录、当前用户、退出登录、邮箱限速。
- **账号**：创建、列表、详情、修改显示信息、停用/恢复、重置 Key、重同步预览/执行、删除预览/物理删除。
- **EA 实例与配置**：实例列表、心跳、配置快照、参数分组、过期状态。
- **同步日志**：同步轮次、批次、握手结果、游标、有效订单数、新增/更新/重复/拒绝数、失败原因。
- **原始事实**：Deals、Orders、Positions、Symbols、Snapshots 的跨账号查询、详情和来源追踪。
- **完整交易**：Trade 列表、详情、成员、问题、风险、手工修正、重新构建、范围外处理。
- **标签**：标签组、标签、批量应用、停用、删除、合并预检、合并执行和审计。
- **模型与规则**：Setups、Playbooks、版本、规则、版本差异、发布、停用、规则评估。
- **复盘**：复盘状态、笔记、情绪、错误、结论、下次行动、版本保存、冲突检测、附件。
- **分析**：总览、模型/规则、时间、错误、执行、计划、标签、下钻、导出任务。
- **每日闭环**：日计划、场景、版本修订、意图、日总结、周复盘、行动、习惯、提醒、交易日历。
- **工作区设置**：时区、交易日切、交易时段、币种展示、默认筛选、通知偏好。

### 7.5 统一接口约定

列表接口统一支持：

- 分页：`page`、`page_size`，响应返回 `items / page / page_size / total / total_pages`。
- 排序：`sort=[{field,direction}]`，禁止前端任意传 SQL 字段。
- 筛选：账号、日期、币种、品种、方向、模型、标签、复盘状态、完整性、规则结论。
- 稳定排序：业务时间相同时追加主键或唯一事实 ID。
- 时间范围：请求携带时区和日切，服务端以 UTC 存储、按口径计算。
- 金额：响应包含数值和币种，不把不同币种合并成无说明总额。
- 幂等：批次上传、附件确认、危险操作执行使用幂等键或操作令牌。
- 错误：统一错误码、消息、字段级错误、是否可重试、请求追踪 ID。

### 9.2 标准数据夹具

至少构造以下数据集，并在测试和演示环境中复用：

1. 简单无加仓交易：一单开仓、一单平仓，含佣金、库存费、止损止盈。
2. 一次开仓三次部分平仓：最终只形成一个完整交易。
3. 相邻两笔独立同向同品种交易：不能因时间接近而错误合并。
4. 跨日持仓：每日已实现账按发生日，完整交易归属最终结束日。
5. 只有平仓或缺少开仓：Trade 标记待核对，不制造虚假持仓时长和胜率。
6. 数量不平、反向成交、净持仓/对冲模式冲突：输出问题并等待确认。
7. 重复同步和同批次重试：新增数不膨胀，游标安全。
8. 多账号不同币种：金额分币种统计，不自动汇兑。
9. 缺初始风险：金额统计保留，R 不计算并显示有效样本数。
10. 规则覆盖不足、全部 N/A、空规则：均不产生误导性分数。
11. 迟到交易、计划修订、休息日、无交易日：每日流程状态正确。
12. 重同步和账号删除：人工资料恢复、范围外、共享定义和物理清理符合要求。

### 9.4 代码质量门禁

- Python：Ruff/Black 或统一格式化、类型标注、mypy 逐步开启、关键服务单元测试。

## 10. 安全、隐私与审计

### 10.1 身份与权限

- Web 用户登录继续使用邮箱验证码；验证码短时有效、限流、防枚举、防暴力重发。
- Web API 使用登录态令牌；EA API 使用每账号独立 Bearer Key 和 HMAC，不共用 Web Token。
- 所有查询从当前用户和账号归属双重校验，禁止仅凭前端传参访问交易、附件或导出文件。
- 重置 Key 后旧 Key 立即失效；账号停用或删除后旧 EA 请求不能写入，也不能重建账号。
- 管理操作记录操作者、时间、原因、影响范围和请求追踪 ID。

### 10.2 数据保护

- `.env`、证书、私钥、SQLite 数据库、邮件凭证、附件原始文件不得提交 Git。
- EA Key 在数据库中以安全哈希或加密形式保存，页面只在创建/重置时展示一次。
- 附件落盘到私有目录，文件名使用不可猜测的存储键；访问通过鉴权接口。
- 删除账号或附件后，私有访问入口立即失效；备份保留周期和物理清理时间需要明确。
- 导出文件设置有效期，过期自动清理；导出记录保存范围、口径、币种和生成时间。
- 日志保存核心接口元数据、数量和标识号；订单详情、截图内容、验证码、Key、Token 不进日志。

### 10.3 输入与网络安全

- 所有用户输入使用 Pydantic/Zod 校验；富文本如需使用，首版采用纯文本或安全白名单。
- 排序、筛选、批量操作必须使用后端白名单，防止 SQL 注入和越权批量更新。
- 文件上传限制类型、大小和数量；上传内容与扩展名、MIME、图片头校验一致后才可预览。
- HTTPS 局域网证书配置写入文档；开发证书与生产证书分离。
- CORS、可信 Host、代理头和 Next.js BFF 转发按最小权限配置。
- HMAC 增加时间窗口和重复请求检测，拒绝明显过期时间戳。

### 10.4 审计范围

必须可在控制台查询审计/同步日志，但只显示核心内容和数量：

- 登录、验证码发送、账号创建、Key 重置、停用/恢复。
- 同步开始、批次接收、批次确认、游标提交、失败和重试。
- Trade 归并修正、风险补录、规则人工覆盖、标签合并。
- 计划修订、复盘冲突、附件删除、导出、重同步、彻底清空、账号删除。

审计日志不能包含订单价格、手数、盈亏、止损止盈等订单明细；同步日志可以包含 ticket/order/position 标识号及数量。
## 11. 部署、运行与数据维护

### 11.1 本地与局域网开发

- FastAPI 继续监听局域网地址，使用 HTTPS；当前已验证的端口可沿用 `8443`，避免与旧服务冲突时再调整。
- Next.js Studio Admin 前端以 HTTPS 或可信代理方式开放局域网访问，手机和桌面浏览器都要验证。
- 前端只向浏览器暴露自身 BFF/API 路由；EA Key 不写入浏览器 Local Storage。
- 后端 CORS 只允许配置中的前端来源；健康检查不返回敏感配置。
- 提供一键启动脚本：启动后端、前端、显示本机/局域网地址、检查端口和证书状态。

### 11.2 正式运行建议

首版可继续单台 Windows 局域网部署，但按正式应用方式管理：

1. 使用独立配置文件和数据目录，不依赖开发者终端。
2. FastAPI 通过 HTTPS 服务或反向代理运行；Next.js 使用 `standalone` 构建。
3. SQLite 文件、附件目录、导出目录纳入每日备份。
4. 后端和前端分别记录运行日志，配置日志轮转和磁盘容量告警。
5. 服务重启后 EA 重试不能产生重复数据；游标和批次状态可恢复。
6. 数据恢复每阶段至少演练一次：空库迁移、现有库升级、备份恢复、附件一致性检查。
7. 当多设备写入、并发分析或数据量增长到 SQLite 不适合时，再迁移 PostgreSQL；Repository 层不得使用不可迁移的私有 SQL 写法。

### 11.3 数据备份

- SQLite 备份使用 WAL checkpoint 后复制或在线备份 API，避免只复制半个 WAL 状态。
- 附件与数据库备份使用同一批次标识，恢复时校验附件引用。
- 删除账号前生成用户可见的影响范围；是否允许删除前自动归档由设置决定，默认不把归档当作物理删除。
- 导出文件和临时上传分片定期清理，失败上传不长期占用配额。

### 11.4 监控指标

- 服务：进程状态、HTTPS 健康检查、启动时间、错误率、响应耗时。
- 同步：最近心跳、最近成功同步、待确认批次、失败批次、旧轮次拒绝数。
- 数据：待核对 Trade、未分配费用、缺风险 Trade、同步数量与构建数量差异。
- 存储：SQLite 大小、附件数量与容量、导出文件数量、日志磁盘占用。
- 安全：验证码发送频率、登录失败、HMAC 失败、越权拒绝、附件鉴权失败。

## 12. 风险、决策点与待确认事项

| 事项 | 风险 | 当前处理 | 必须确认的时点 |
|---|---|---|---|
| EA 能否提供订单、持仓关联、初始止损和风险事实 | 无法准确构建复杂 Trade 或 R | Deal 先保持兼容；风险可人工补录并标记来源 | M2 构建器和 M4 R 指标开发前 |
| 净持仓与对冲模式差异 | 同向相邻交易可能错误合并 | 不唯一即待核对，不强行归并 | 使用真实账号样本验证时 |
| 经纪商费用正负号和入账时间 | 每日已实现账可能错误 | 保留原始字段，费用时间缺失时仅用于整笔统计并提示 | M2 样本核对时 |
| MT5 服务器时区 | 页面显示或交易时段误判 | 全局显示 MT5 时区；事实用 UTC，展示按时区配置 | M1 心跳/账号详情上线前 |
| 交易日切和时段定义 | 时间分析结果不符合用户习惯 | 设置中配置北京时间、日切和主时段，规则可追溯 | M5 时间分析开发前 |
| 附件规模 | 磁盘压力和上传失败 | 限制类型/大小/数量，私有存储和定期清理 | M3 附件开发前 |
| 账号删除与共享文本 | 可能误删共享规则或残留账号引用 | 专属物理删除、共享定义保留、自由文本提示手动处理 | M7 删除功能验收前 |
| 旧 EA 不支持批次字段 | 无法使用完整握手 | 新字段可选，旧 EA 走兼容路径；仍保留两阶段游标 | M1 联调时 |
| Studio Admin 版本升级 | Next.js 16/React 19 依赖变化 | 锁定 package-lock，模板改动以业务组件扩展为主 | 脚手架创建时 |
| SQLite 并发限制 | 大批量同步和分析互相影响 | 短事务、分页、索引、WAL；必要时迁移 PostgreSQL | 数据量压测后 |

需求文档中的业务默认值进入实现前仍允许评审调整；一旦进入某里程碑开发，变更应记录为产品决策并更新验收标准。

## 14. 开发顺序结论

建议立即从 **M0 工程基线 + M1 同步握手/账号/原始订单** 开始。这样可以保留现有成果，先解决最关键的数据可信问题，再在稳定事实层上逐步构建 Trade、复盘、规则、分析和每日闭环。

M1 完成并通过真实 EA 联调前，不建议并行开发大量分析或计划页面；否则后续 Trade 口径、同步批次和数据完整性变化会造成返工。
